# 非同期 RPC の設計（メモ）

- 作成：2026-11-16
- 状態：設計の方針。段 A を実装済み（2026-11-16）。段階の順を組み替えた（2026-11-26、第 7 節）：最初の例はロックステップの車と人の移植、2 つ目の例は ServoJ、状態推定は最後

## 1. 目的と方針

robot-runtime に、外の人がプラグインとして RPC サービス（「この関節角へ動かして、着いたら返して」「今の状態を返して」など）を足せるようにする。

### 1.1 ゴール：3 つの軸

| 軸 | 中身 | 節 |
|---|---|---|
| 1. ステップを止めないサービス | 要求は好きな実時間のタイミングで届き、来なくてもステップは進む。「受け付けたらすぐ返す」から「N ステップかけて動かし、終わったら返す」まで、同じ形で書ける | 第 3〜5 節 |
| 2. ロックステップの旧ルートの統合 | CARLA 比較の車と人（`AsyncRpcInput`、全員の要求がそろうまで止める）を、軸 1 の上のプラグインの例として作り直し、ルートを一本にする | 第 6 節 |
| 3. 状態推定 | コントローラ（サービスも含む）が見るのは、真の値ではなく観測と推定 | 第 3.2 節 |

3 つとも同じ土台（1 ステップのパイプライン）の上に乗せる。どれか 1 つのために、ほかと別の通り道を作らない。

### 1.2 最初の例：ロックステップの車と人を移す

設計を端から端まで一本通す最初の例は、今の旧ルートで動いている CARLA 比較の車（`AckermannStep`）と人（`PersonStep`）を、サービスとして書き直すこととする（2026-11-26 決定）。

- **正解がもう手元にある**：旧ルートには結合テストと Urban の決定性（同じ入力でステップの記録が同じ）がある。新ルートで同じシナリオを動かし、記録がビット単位で同じなら、設計どおりに動いたと言える。
- **0 ステップで完了するサービスになる**：旧ルートの車は、ステップ k の要求を受け、そのステップの物理の後に応答（pose・twist・時刻）を返す。サービスで書くと、`on_request` で指令を置き、最初の `on_step` で完了を返す形。違いは、サービスの設定でロックステップ（第 6.2 節）を指定することだけ。サービスのコードは非同期のときと同じ。
- **N 台は、1 台のサービスを N 個並べる**：第 4.2 節（1 サービス 1 クライアント）のとおり、車ごとに別のサービス（`CarService/AckermannStep/<車>`）にする。共通ルートのステップの門は、ロックステップの全サービスの要求がそろうまで進めないので、「全台そろうまで進めない」は門の決まりから出てくる。複数台をまとめた別のサービスは作らない。人も同じ。
- **軸 2 がそのまま片付く**：記録が同じことを確かめたら、旧ルート（`AsyncRpcInput` と `HAKO_ENABLE_ASYNC_RPC_INPUT`）を消せる。
- 旧ルートが 1 か所でまとめて持っているものを、各サービスに分ける：

| 旧ルート（`AsyncRpcInput` が全台分をまとめて持つ） | 新ルート（サービスごと） |
|---|---|
| 全台の要求がそろったら、まとめて当てる（apply batch） | 各サービスが自分の要求を当てる。どれも物理の前なので、結果は変わらないはず |
| 次に来るべきステップ k | コアが「1 ステップに 1 要求」を保証する。番号を確かめたいサービスは `on_request` で断る |
| タイムアウト（最初と 2 回目以降）と、来ていないチャネルのログ | 共通ルートのステップの門が持つ（第 6.2 節） |
| ステップの記録（`step_log_path`、全台分を 1 つのファイル） | 未決（第 8 節） |

最初の実装は C++ の `IAsyncService` として書き、記録が同じことを確かめてから、プラグインの C の境目（段 E）に移す。

### 1.3 2 つ目の例：Dobot NOVA5 の ServoJ

2 つ目の例は、Dobot NOVA5 の `ServoJ`（hakoniwalab/hakoniwa-robot-runtime#30、teras-project/hakoniwa-robot-arm#8）とする。ServoJ は例の 1 つで、設計を ServoJ に合わせて狭めはしない。

- ServoJ は、要求を受け付けたらすぐ応答を返す**同期の RPC**。動きはそのあと、ロボットが目標へ向かう。クライアントは要求を次々に送り、目標を更新し続ける。
- この設計では「**0 ステップで完了するサービス**」になる。`on_request` で最新の目標を置き換え、最初の `on_step` で完了（受付 OK）を返す。応答は、要求を受けた箱庭のステップの終わり（物理の後）に出る。すぐ完了するので、次の要求が来ても BUSY にならない。
- 動き（今の位置から最新の目標へ、決まった時間をかけて近づける）は、サービスの外の、ふつうのコントローラが受け持つ。サービスは目標を渡すだけ。
- 応答の遅れは最大で箱庭のステップ 1 回分。実機の ServoJ は短い間隔で送るので、箱庭のステップは送る間隔より十分短くする（例：2 ms）。
- 引数（目標に着くまでの時間など）の意味は、段 S1 で Dobot の資料を確かめて決める。
- **ServoJ に取りかかるときに決めること**（2026-11-26、森）：ServoJ はロックステップではなく非同期。要求を受けたら目標を置き、要求ごとに即応答し、腕は目標に向かって動き続ける。今の決まりでは、応答（DONE）でサービスの処理は終わり、次の要求まで `on_step` は呼ばれないので、「動き続ける」をどこで回すかを決める。案 A：目標を読む普通のコントローラが動かす（サービスは 0 ステップで完了。車と同じ関係）。案 B：応答とは別に、サービスの `on_step` を毎刻み呼び続ける選び方をコアに足す（書き味はよいが、「応答 ＝ 処理の終わり」の決まりを崩す）。

ServoJ に要るのは、2 つの速さ（段 B0）、サービスの部品（段 B）、ServoJ のサービスとコントローラ（段 S1〜S3）。車と人の移植（第 1.2 節）で同じ「0 ステップで完了するサービス」が通ったあとなら、足すのは ServoJ の中身と ROS からの入口だけになる。

方針は一つ：**RPC のセッション管理は hakoniwa-core-pro に任せ、robot-runtime 本体には持たない。**

- 要求の受付、キャンセルの受付、状態（DOING・CANCELING・DONE）、進捗、結果コードは、core-pro の RPC サービスがすでに共有メモリの上で持っている。
- タイムアウトの監視はクライアントの責務（core-pro の決まり）。サーバ（robot-runtime の側）は時間を数えない。
- キャンセルが来たときにどうするか（その場で止まる、減速して止まる、途中の姿勢を保つ など）は、サーバのプログラム、つまりプラグインが決める。robot-runtime はキャンセルの到着をプラグインのフックに渡すだけで、その結果は core-pro の仕組み（結果コード CANCELED の応答）で返す。

こうすると、robot-runtime 本体の仕事は「サービスの準備」と「毎ステップ、決まった順にプラグインのフックを呼ぶこと」だけになる。

もう一つ：**サービスは、今ある 1 ステップのパイプラインに、今ある型を継承した部品として乗せる。** ランナーの横に別の入力を置かない。共通の処理に「サービスなら」「ロックステップなら」の分岐を入れない（第 3.1 節）。

## 2. 今あるもの（2026-10-27、Urban の車と人のため）

| 部分 | 中身 |
|---|---|
| サービスの準備 | アセットの登録の直後に、Runner が `hako_asset_service_initialize(サービス定義)` を呼ぶ。各サービスのサーバは、そのあと `hako_asset_service_server_create` で作る |
| 汎用の通り道 | `IAsyncRpcChannel`（実体は `CoreAsyncRpcServiceChannel`）。`poll` で要求を受け取り、`reply` で応答を返す。中身は「ステップ番号 + 型を決めないデータ」 |
| ステップとの合わせ方 | `AsyncRpcInput`。物理の前に要求を指令に変えるフック（apply）、物理の後に応答を作るフック（build_response） |
| 使っている例 | 車 `CarService/AckermannStep/<車>`、人 `PersonService/PersonStep/<人>` |
| サービス定義を作る道具 | `tools/gen_rpc_service_config.py`（サービス定義の JSON と起動の引数） |
| ビルドの切り替え | `HAKO_ENABLE_ASYNC_RPC_INPUT`。有効にしているのは Urban のビルドだけ |

足りないもの：

1. 型ごとのフックが本体に組み込まれている（車と人）。外から足す口がない。
2. 待ち方がロックステップだけ。全ロボットからステップ k の要求がそろうまで物理を進めない。「要求が来たら答え、来なくてもステップは進める」形がない。
3. キャンセルを誤りとして扱っている。`poll` が `REQUEST_CANCEL` を受けると、誤りとして止まる。
4. サービス定義の道具が、車と人の 2 種類の型しか知らない。

## 3. 責務の分担

| 担い手 | 持つもの | 持たないもの |
|---|---|---|
| hakoniwa-core-pro | 要求・応答の受け渡し、キャンセルの受付、状態、進捗、結果コード | ロボットの意味 |
| クライアント（外のアセット、コントローラ、シナリオ） | 要求を出す、タイムアウトを監視する、必要ならキャンセルを出す | ロボットの内部 |
| robot-runtime 本体 | サービス定義の読み込み、サーバの作成、毎ステップのフックの呼び出し、イベント（要求・キャンセル）をフックへ渡す、フックの結果を core-pro の API へ渡す | セッションの状態、タイムアウト、キャンセル後の振る舞い |
| プラグイン | 要求の中身の解釈、指令の作成、完了の判断、キャンセルされたときの振る舞い、応答の中身 | 共有メモリ、サービスの準備 |

### 3.1 1 ステップの中の置き場所（基礎設計）

robot-runtime の 1 ステップは `ActuatorRuntime::step()` が回す。MuJoCo の step は、この中のプラントで 1 回だけ呼ぶ。

```text
状態を読む → command source → controller → arbiter → plant（MuJoCo step）→ sensor → publish
```

今のパイプラインは pub/sub の形をしている。指令の入口（command source）が新しい入力を受け、コントローラが指令に変え、Arbiter が選び、プラントが進め、publisher が状態を出す。非同期のサービスも同じ形に乗る。

```text
状態を読む
→ command source … サービスの受け口：core-pro を poll（ロックステップなら門が取っておいたもの）。要求なら on_request、キャンセルなら on_cancel。結果をコントローラへの入力にする
→ controller     … 処理中なら on_step（指令と完了か）
→ arbiter        … 今のまま
→ plant          … 今のまま（MuJoCo の step はここだけ）
→ sensor         … 今のまま
→ publish        … 完了していたら、core-pro の入れ物を用意し、on_response で中身を書いて送る
```

| 段 | 今ある型 | サービスの部品（robot-runtime が持つ） | すること |
|---|---|---|---|
| command source | `ICommandSource` | サービスの受け口 | core-pro のサーバを service_id で `poll` する（ロックステップのサービスは、門が取っておいた要求を受け取る）。要求なら `on_request` を呼び、断られたら INVALID の応答を予約する。キャンセルなら `on_cancel`。受け付けた要求・キャンセルを、コントローラへの入力にする。何も来ていなければ入力なし |
| controller | `IController` | サービスのコントローラ | 入力が受け付けた要求なら処理中に、キャンセルなら CANCELING にする。処理中なら毎刻み `on_step(状態, 時刻)` を呼び、指令と完了かを受け取る。待機中は指令を出さない（Arbiter に選ばれない） |
| arbiter・plant・sensor | 今のまま | 変えない | |
| publish | `IStatePublisher` | サービスの応答 | 完了していたら、物理の後に core-pro の応答の入れ物を用意し（頭に状態 DONE と結果コード）、`on_response(物理の後の状態, 入れ物)` で中身を書かせて送り、待機に戻す |

- 3 つの部品は、1 つのサービス（`IAsyncService`）と、そのサービスの core-pro のサーバ（service_id）を共有する。ユーザが書くのは `IAsyncService` だけ。プラグインになっても同じ（第 5 節）。
- 部品は今ある型を継承するだけで、パイプラインの本体（`ActuatorRuntime`）にはサービスのための分岐を入れない。組み立ては工場（factory）が、今の車の受け口やコントローラと同じようにする。
- コントローラは、入力のないステップにも毎回 `update` が呼ばれる（今の決まり）。だから処理中の `on_step` を毎ステップ呼べる。
- **`on_request` は受け口の段で呼ぶ**（2026-11-26 に直した。前の版はコントローラの段だった）。受け口の段は、すべてのコントローラより前に動く。だから `on_request` で置いた目標や指令は、同じ刻みのほかのコントローラ（車の Ackermann のコントローラなど）が、ふつうの入力として読める。旧ルートの「ステップの前に指令を置く」と同じ刻みになる。コントローラの段で呼ぶと 1 刻み遅れ、それを埋めるためにコントローラが自分で入力を読みに行く抜け道が要った（段 P1 で分かった）。
- 応答は publish の段（物理の後）で作って送る。だから物理の後の状態（着いた位置、車の pose・twist など）を応答に入れられる。`on_step` は応答の中身を返さない（2026-11-26 に直した。前の版では `on_step` が中身を返す書き方と、物理の後に作る書き方が混ざっていた）。
- 応答の入れ物は core-pro が用意する（`get_response_buffer`）。頭（状態、結果コード、どの要求への応答か）は core-pro が書いたものを残し、サービスは中身（body）だけを書く。旧ルートの車の応答の書き方（入れ物を読み、中身だけを書き換えて戻す）と同じ。
- 応答の中身を作るのはユーザ（サービス）で、コアは作らない。コアは「いつ」（物理の後）と「入れ物」（頭）を受け持ち、ユーザの `on_response` を呼ぶ。呼ぶのはサービスの応答の部品（コア側の publisher の 1 つ）で、共通ルート（`ActuatorRuntime`）は変えない。旧ルートの `AsyncRpcBuildResponse`（ランナーに埋め込まれたもの）とは別物で、旧ルートを消す段 J で一緒に消える。
- core-pro のサーバの呼び出し（`server_create`・`poll`・`get_request`・`get_response_buffer`・`put_response`）は、service_id で呼ぶ小さな窓口 1 つにまとめる。テストでは偽物に替える。
- 旧ルート（`AsyncRpcInput`）は、ランナーに専用の呼び出し（要求を当てる・応答を返す）を持っている。新ルートは持たない。

**2 つの速さ（2026-11-16 決定）**：外とのデータのやり取りは箱庭のステップで、制御と物理は物理のステップで動く。

| 速さ | 段 | すること |
|---|---|---|
| 箱庭のステップ（境目に 1 回） | command source | 外からの入力を受ける（PDU、RPC の要求とキャンセル） |
| 物理のステップ（刻みごと） | controller → arbiter → plant → sensor | 制御、選択、物理、センサの読み取り |
| 箱庭のステップ（境目に 1 回） | publish | 外へ出す（状態、センサの値、RPC の応答） |

- 背景：今まではおもに pub/sub で、箱庭のステップと物理のステップが同じだったので、違いが見えなかった。旧ルートで、外（シナリオ）が 10 ms ごとに要求を投げてくる一方、物理は 1 ms で刻む（`physics_substeps`）ことが分かり、2 つの速さを分ける必要が出た。
- 今の作りは、command source を物理の刻みごとに `poll` する。外のアセットは別のプロセスで書き込むので、要求が刻みの何回目で見えるかが実時間で変わり、結果が決まらない。外の時刻が進むのは箱庭のステップの境目だけなので、入力もそこでだけ受ける。
- サービスでは、要求とキャンセルを境目で受け、`on_step` は刻みごとに呼び（細かく制御できる）、応答は境目で返す。刻みの途中で完了したら、その刻みから `on_step` を呼ばず指令も出さない（残りの刻みはほかのコントローラが選ばれる）。応答は境目で送る。
- 刻みが 1 なら、全部が毎ステップ 1 回で、今と同じ。
- これは共通の土台の直し：`ActuatorRuntime::step()` に、今の「出力するか」（`publish`）に並べて「入力を受けるか」を足し、ランナーは最初の刻みだけ受ける（段 B0）。

### 3.2 コントローラが見るのは観測と推定（2026-11-16 決定）

サービスの `on_step` に真の値を渡すと、サービスのコードが「真の値が見える」前提で書かれ、推定（EKF）を入れるときに書き直しになる。これはサービスだけでなく、コントローラ全員に共通の話なので、共通の土台を直す。

今の作り（コードで確かめた）：

- コントローラは全員、ステップの頭でプラントから読んだ真の値（関節、剛体）を見ている（`ActuatorRuntime::step` の 1）。
- センサの段（`ISensorStage`、`MujocoSensorStage`）は物理の後で真の値からセンサの値を作り `RobotState::sensor_readings` に書くが、使うのは publish だけで、コントローラには届かない。
- 推定の考え方はない。コントローラのプラグインの関節の状態の出どころ「観測値」（`PluginJointStateSource::Observed`）は TODO で、選ぶと断られる。
- お手本は Drone PRO：`IStateEstimator`（センサの値と、記録用の真の値を入れ、推定値と「準備ができたか」を出す）。順は 真の値 → センサ → EKF → 制御 → 物理。Control Link の仕様も「制御に入るのは観測できる値で、真の値ではない」。

決めた形：

```text
（前の物理の後）プラント → センサの段（今ある）→ 推定の段（新しい）
                                         ↓ 「コントローラが見る状態」を作って持つ
（このステップ）入口 → コントローラ（全員。サービスの on_step も）→ Arbiter → プラント …
```

- **推定の窓口**は Drone PRO の `IStateEstimator` と同じ形：入力はセンサの値・時刻・真の値（真の値は記録と簡略版のためだけ）、出力は推定値（関節の位置・速度、剛体の位置・姿勢・速度）と「準備ができたか」。今回は**真の値をそのまま返す簡略版**だけを入れる。
- **コントローラが見る状態**は、推定の段のあとで推定値とセンサの値から作り、次の刻みのコントローラに渡す。形は今の `RobotState` のまま（関節と剛体の欄に推定値、センサの値の欄にセンサの値）。だから**コントローラの関数の形は変わらない**。組み込み、プラグイン、サービスのどれも書き直さず、中身だけが観測できるものになる。プラグインの「観測値」の TODO もこれで埋まる。
- 簡略版は真の値を返すので、切り替えの ON と OFF で結果がビット単位で同じになるはず。それを確かめのテストにする。
- 座標は NWU（世界）・FLU（センサ）。四元数の並びは sensor adapter が wxyz、`RobotState` の剛体が xyzw なので、境目ごとに明記する。
- C の境目（段 E）では、推定値の関節を今の `HakoJointStatesV1` で渡す。剛体の推定値とセンサの値の C の型は段 E で足す。

### 3.3 切り替え（ifdef）

## 4. サービスの持ち方（core-pro のサービスのモデル）

### 4.1 core-pro が持つもの

| もの | 中身 |
|---|---|
| サービス定義（`service.json`） | サービスごとに、名前（例 `Service/Add`）、型（例 `hako_srv_msgs/AddTwoInts`。要求と応答の PDU の型が決まる）、`maxClients`、PDU の大きさ（サーバ側とクライアント側の `baseSize`・`heapSize`）。`hako_asset_service_initialize` が読み込み、共有メモリにサービスの表を作る |
| service_id | `hako_asset_service_server_create(アセット名, サービス名)` が返すサービスの表の番号。サーバ側の API はすべてこの番号で呼ぶ |
| client_id | クライアントが `hako_asset_service_client_create(アセット名, サービス名, クライアント名)` でつながるたびに 0 から振られる。クライアントごとに要求用と応答用の PDU チャネルを持つ |
| 状態 | クライアントごとに IDLE・DOING・CANCELING。結果コード（OK・ERROR・CANCELED・INVALID・BUSY）、進捗も持つ |
| 実行のまたぎ | サーバのオブジェクトは実行をまたいで残る。新しい実行が始まると core-pro が状態を戻す（core-pro #109）。robot-runtime はリセットしない |

### 4.2 1 サービス 1 クライアント

core-pro は 1 つのサービスに複数のクライアントを定義できる（`maxClients`）。ただしサーバ側は「今のクライアント」（`current_client_id`）を 1 つだけ見て順に回す作りで、要求のヘッダと中身を入れる場所がサービスに 1 つしかない。複数のクライアントが同時に要求すると取り違えうる。

今回は **1 サービス 1 クライアント**（`maxClients: 1`）とする。同じ型のサービスでも、クライアントごとに別のサービス名にする（車の `CarService/AckermannStep/<車>` と同じ形）。`maxClients` が 1 でない定義は、起動時に止める。

### 4.3 robot-runtime が知っておく情報

robot-runtime が持つのは「サービス名と型」（定義から）と「service_id」（作ったときに受け取る）だけ。ほかの状態は毎回 core-pro に聞く。

| 情報 | どこから | 何に使う |
|---|---|---|
| サービス名 | プラグインの `describe` → サービス定義 | `server_create`、ログ |
| 型（要求・応答の PDU） | 同上 | 要求を解く・応答を作る（中身の変換はプラグイン。要求は頭を含む PDU のまま渡し、応答は core-pro が頭を書いた入れ物に中身だけを書く） |
| PDU の大きさ | サービス定義 | 応答の入れ物の確認 |
| `maxClients` | サービス定義 | 1 以外なら起動時に止める |
| service_id | `server_create` の戻り値 | `poll`、`get_request`、`get_response_buffer`、`put_response`、`set_progress`、`server_status` |
| 今のクライアント（client_id） | `server_get_current_client_id` | ログ・診断（1 クライアントなら常に 0） |
| 状態（IDLE・DOING・CANCELING） | `server_status` | プラグインに進行中の要求があるかを渡す |

## 5. プラグインの形

### 5.1 分担

定型の処理はすべて robot-runtime が持ち、プラグイン（ユーザ）は「要求の中身の解釈」「プラントへの指示」「完了の判断」だけを書く。

| robot-runtime が持つ | プラグインが持つ |
|---|---|
| `poll`、要求の取り出し（`get_request`）、キャンセルの受け付け、応答の入れ物の確保と送信（`get_response_buffer`・`put_response`、状態と結果コード）、進捗の送信（`set_progress`） | 要求のバイト列を自分の型に変換する、中身を確かめる、プラントへの指示を出す、完了（または止め終わり）を判断する、応答の中身を作る |

プラグインに渡すのは service_id と要求のバイト列だけで、ステップ番号のような旧ルートの考え方は持ち込まない。

### 5.2 境目は C

- C の型と関数だけが境目を越える（コントローラのプラグイン、外部センサプラグインと同じ決まり）。robot-runtime とプラグインを、違うコンパイラや違うビルド設定で作っても壊れないようにするため。C++ の抽象クラスは、コンパイラが違うとメモリの並びが合わないことがある。
- 要求は「service_id、サービス名、型の名前、PDU のバイト列」で渡す。プラグインは service_id（またはサービス名）を見て自分のものなら、生成済みの変換関数（`pdu_cpptype_conv_*`）で自分の C++ の型に変換する。応答は、robot-runtime が core-pro の入れ物（頭は書いてある）を渡し、プラグインが自分の型から中身を書き込む。プラグインは頭を書き換えない。
- プラグインの中で抽象クラスの書き味にしたいときのために、C の境目の上に薄い C++ のヘッダを用意してもよい（プラグインの中だけで閉じる）。

### 5.3 フック

| フック | いつ | プラグインがすること | 返すもの |
|---|---|---|---|
| `describe` | 読み込み時 | 提供するサービス名と、要求・応答の型を返す | サービスの一覧（サービス定義を作る道具が使う） |
| `on_request(service_id, 要求)` | 受け口が `REQUEST_IN` を受けた箱庭のステップの、**command source の段**（すべてのコントローラより前、物理の前） | 要求を自分の型に変換し、中身を確かめ、受け付けるならプラントへの指示を始める | 受け付けた／受け付けない（受け付けないなら robot-runtime が結果コード INVALID で応答する） |
| `on_step(service_id, 状態, 時刻)` | 進行中の要求があるサービスについて、毎ステップ controller の段（物理の前。前のステップの物理の後の状態を見る）。状態は core-pro のサーバの状態そのまま（DOING＝処理中、CANCELING＝キャンセル中） | プラントの状態を見て、指示を続ける。CANCELING なら止め方に切り替える。完了か（キャンセル中なら止め終わったか）を判断する | まだ／完了（OK）／止め終わった（CANCELED）／失敗（ERROR）と、そのステップの指令。任意で進捗。応答の中身は返さない |
| `on_cancel(service_id)`（任意） | 受け口が `REQUEST_CANCEL` を受けた箱庭のステップの、command source の段（`on_request` と同じ） | キャンセルが来たことの通知だけ。記録やログなど、来た瞬間を知りたいプラグイン向け。実装しなくてよい | なし |
| `on_response(service_id, 状態, 時刻, 入れ物)` | `on_step` が完了・止め終わった・失敗を返した箱庭のステップの、publish の段（物理の後）。`on_request` と対になる「出る」側のフック | 物理の後の状態から応答の中身を作り、core-pro が用意した入れ物の中身（body）に書く。頭は書き換えない。**必須**（`on_request` と対）。core-pro は入れ物を使い回し、頭しか書き直さないので、書かないと前の応答の中身が残る。中身の欄は毎回すべて書く | 書けた／書けなかった（書けなければ robot-runtime が誤りとして止める） |
| `reset`、`destroy` | リセット、終了 | 進行中の要求とプラントへの指示を捨てる | なし |

- `on_step` は指令と「完了か」を 1 回で返す。「完了」「止め終わった」「失敗」を返すと、そのステップの publish の段（物理の後）で `on_response` を呼び、応答を送る（状態 DONE、結果コード OK・CANCELED・ERROR）。
- `on_request` が断ったときは `on_response` を呼ばない。そのときの中身は前の応答の値が残りうるので、クライアントは結果コード INVALID を見たら中身を読まない（決まり）。応答は core-pro の入れ物のまま（結果コード INVALID）送る。
- 通知と処理を分ける：`on_cancel` は通知だけで、それ以上でもそれ以下でもない。キャンセルの処理（止め方の切り替え、止め終わりの判断）はすべて `on_step` でする。`on_cancel` を書かないプラグインも、`on_step` の状態だけで正しく動く。
- 指令は、アクチュエータを直接は触らず、サービスのコントローラの出力として Arbiter に出す。最後の選択（Arbiter）と安全の検査（範囲、期限、有限の値）は、今までどおり robot-runtime が持つ。状態は読み取りだけ。
- フックはシミュレーションのスレッドで、ステップの間に呼ばれる。プラグインは待たずにすぐ戻る。

### 5.4 core-pro が保証していること

core-pro のサーバは、要求の受け付けを状態で管理している（`hako_service_protocol_server.cpp` の `poll`）。

| サーバの状態 | 要求が来た | キャンセルが来た |
|---|---|---|
| IDLE（処理していない） | サーバに届く（`REQUEST_IN`）。状態は DOING に | 警告を出して捨てる |
| DOING（処理中） | core-pro が BUSY で応答し、サーバには届けない | サーバに届く（`REQUEST_CANCEL`）。状態は CANCELING に |
| CANCELING（キャンセル中） | core-pro が BUSY で応答する | 同上（BUSY） |

このため、`on_request` は処理していないときにしか来ない。処理中に同じサービスから来た要求を robot-runtime が弾く必要はない。

**ただし（2026-11-26 に分かった core-pro の不具合、hakoniwalab/hakoniwa-core-pro#122）**：今の core-pro は、BUSY や処理中の進捗（DOING）といった途中の知らせも、最後の返事と同じ `reply()` で送る。`reply()` は送るたびにサービスを完了（IDLE）にし、担当のクライアントを切り替えるので、BUSY を返すと処理中のサービスが終わったことになり、本当の完了の返事が届かない。0 ステップで完了するサービス（車と人の移植、ServoJ）には影響しない。時間のかかるサービス（段 C・D、G）と進捗は、#122 が直るまで使えない。robot-runtime の結合テスト 23（処理中の 2 つ目の要求）は、それまで既知の失敗として外す。

### 5.5 プラントの隠し方と Arbiter（今ある仕組みに乗る）

プラグインには MuJoCo を見せない。robot-runtime はすでに、物理エンジンに依存しない形でプラントと状態を持っている。

| 仕組み | 今ある形 | サービスのプラグインでの使い方 |
|---|---|---|
| プラント | `IActuatorPlant`（MuJoCo は実装の 1 つ `MujocoActuatorPlant`）。本体は「状態を読む」「指令を渡して 1 ステップ進める」だけを知る | プラグインはプラントに直接触らない |
| 状態 | `RobotState`：関節ごとの `ActuatorState`（名前、位置、速度、トルク）、剛体ごとの `BodyState`（名前、位置、姿勢、並進・角速度）、センサの読み | C の境目では、コントローラのプラグインと同じ `HakoJointStatesV1` で関節の状態を渡す。剛体の状態の C の構造体は、要るときに足す |
| 指令 | `ActuatorCommand`（関節、種類、値、期限） | `HakoJointCommandsV1` で返す |
| 時刻 | `HakoTickV1`（シミュレーション時刻、ステップ番号、前のステップで自分の指令が選ばれたか `selected`） | そのまま渡す。`selected` で、自分の指令が実際にプラントへ行ったかを確かめられる |
| Arbiter | `PriorityCommandArbiter`：指令を出せる状態のコントローラのうち、優先度の一番高いものを選ぶ。入力待ちのものは選ばれない | サービスのプラグインを、優先度付きの「コントローラの 1 つ」として載せる。要求を処理している間だけ指令を出し、処理していないときは入力待ち。何もしていないときは保持などのコントローラが選ばれる |
| 安全の検査 | プラントの入口で、種類・期限・有限の値・範囲を確かめる | 変えない |
| プラグインの共通ヘッダ | `HakoPluginHeaderV1` に種類（`kind`）の欄がある | 種類「サービス」を足す。読み込みはコントローラのプラグインの仕組みをそのまま使う |

新しく作るのは「サービスの関数表」と、第 3.1 節の 3 つの部品（受け口・コントローラ・応答）だけ。

## 6. 待ち方

本体の待ち方は一つ：**非同期**。要求が来ていなくてもステップは進む。要求は箱庭のステップの境目で受け、応答はプラグインが完了と判断した箱庭のステップの境目で返す。robot-runtime は要求の到着を待たないので、時間を数える必要もなく、タイムアウトはクライアントだけが持つ。クライアントのタイムアウトは、箱庭の時刻で要求を出した時点から数える合計時間で、処理中の知らせを受けても延びない（core-pro の作り）。時間のかかるサービスは、クライアントがそれより長いタイムアウトを付ける。

待ち方は、サービスの設定で 2 つから選ぶ（2026-11-26 に書き直し）：**非同期**（既定）と**ロックステップ**（`lockstep: true`）。ロックステップはコアの機能で、ユーザはフックを書かない（第 6.2 節）。

| 例 | 待ち方 |
|---|---|
| ServoJ（受け付けたらすぐ返し、目標を更新し続ける） | 非同期。0 ステップで完了するサービス（第 1.3 節） |
| アームの移動の指令（完了で返す）、状態の問い合わせ（その場で返す） | 非同期 |
| CARLA 比較の車（`AckermannStep`）と人（`PersonStep`） | ロックステップ。サービスのコードは非同期の車と同じで、設定だけが違う |

- 今のロックステップの車 RPC（旧ルート）は、CARLA 比較の検証のために作った特殊な実装だった。ロックステップを車や人の型から切り離し、コアの機能として一般にする。
- 混ぜてよい。ロックステップのサービスがあれば、ステップはその要求がそろうまで待ち、その間は非同期のサービスにも新しい要求は届かない（入力は境目でしか受けない）。混ぜて困る組み方をしないのはユーザの責任。
- **一本にする。** 同じような RPC のルートが 2 つあるのはよくない。CARLA 比較の車と人をサービスとして作り直し、今までの結合テストと Urban の決定性（ステップの記録が同じになること）で振る舞いが変わらないことを確かめてから、旧ルート（`AsyncRpcInput`）を消す（第 7 節の段 H・P1〜P3・J）。debris-highway の摩擦も車のサービスの要求に移す（段 J2）。CARLA 比較 P0 は PDU のロックステップで動いており、旧 RPC ではないので、今回は移さない（2026-11-26 決定。PDU 版のロックステップの入力は、pub/sub のロボットのために残す）。最初は C++ のサービスとして作り直し、プラグインにするのはそのあと（段 E）。

### 6.1 Arbiter の束ね方はユーザが決める

Arbiter の決まり（優先度の一番高いグループを丸ごと選ぶ）は変えない。どう束ねるか（車ごとに分けるか、まとめるか）はユーザが決める。robot-runtime は、すべてのコントローラ（車、サービスを含む）の優先度とグループを、アセットのマニフェストで書けるようにするだけ。

- 今は車（Ackermann）のコントローラの優先度とグループがコードに書き込まれている（優先度 10、グループ `ackermann-pdu-direct`）。マニフェストで変えられるようにし、今の値は書かなかったときの既定値として残す（段 C・D）。コントローラのプラグインの `priority` に合わせる。
- 例：全台のサービスと車の指令を同じグループに入れると、関節が重ならない出力がまとめて選ばれる。同じ車に 2 つの指令（サービスと、ふだんの指令）を同時に出さないのはユーザの責任（重なれば Arbiter は何も選ばない）。

### 6.2 ロックステップは共通ルートの機能（2026-11-26 決定、同日に見直し）

ロックステップでやることは、どのサービスでも、どの入力でも同じなので、ユーザには書かせない。ユーザはサービスの設定で `lockstep: true` と指定するだけ。

**置き場所（2026-11-26 見直し）**：「このステップの入力が全員そろうまで、ステップを始めない」は RPC に限らない、**共通ルート（ランナー）の機能**。非同期 RPC のコアが持つのは、「**自分の入力は、このステップの分がもう来ているか**」に答える口の実装だけ（下の「分担」）。最初は非同期 RPC のコアに置いていた（段 H の `AsyncServiceLockstepGate`）が、ほかの口（command source など）と同じ並びにするため、こう分け直す。

**指定する場所（2026-11-26 決定）**：robot-runtime の**アセットのマニフェスト**に、サービスごとの欄を置く（例 `"services": [{"name": "CarService/AckermannStep/Car-1", "lockstep": true}]`）。ロックステップは Runtime の振る舞いなので、core-pro のサービス定義（`service.json`）には混ぜない。既定は `false`（非同期）。ServoJ のような非同期のサービスは `false` のまま。ほかのコントローラの優先度・グループもマニフェストで書く方向（第 6.1 節）と揃える。段 P1 の実装は、まだ起動の引数（`--ackermann-rpc-use-service`）で選び、車のサービスはコードの中で常にロックステップ。段 M（第 7 節）でマニフェストの指定に置き換える。サービスのコード（`on_request`・`on_step`・`on_response`）は、非同期でもロックステップでも同じになる。

**決まり（交互に投げ合う）**

```text
クライアント（シナリオなど）           Runtime（ロックステップのサービス）
  要求 k を送る   ───────────────→  届いた（これが物理を動かす合図）
                                       物理 k を進める
  応答 k を受け取る ←─────────────  物理の後の状態で応答（＝ステップ k の完了）
  応答の状態を見て、次の指令を決める
  要求 k+1 を送る ───────────────→  届いた …
```

1. **物理を動かす合図は、要求が届いたこと**。ロックステップのサービスが複数あれば、全員の要求がそろったとき（最後の 1 つが届いたとき）に、箱庭のステップを 1 つ進める。そろうまでは、物理も箱庭の時刻も進めない。
2. **応答が「前回の処理が完了した」印**。応答は、要求を受けた箱庭のステップの物理の後に出る（0 ステップで完了するサービス）。中身は物理の後の状態なので、クライアントはそれを見て次の指令を決められる。
3. **クライアントは、応答を受け取ってから次の要求を送る**。この交互の決まりで、順番が毎回同じになり、結果が決定的になる。処理中に次の要求が来ることもない（core-pro の BUSY の不具合 hakoniwalab/hakoniwa-core-pro#122 にも当たらない）。
4. **交互の決まりが破られたら、誤りとして止める**。非同期のサービスなら BUSY で断れば済むが、ロックステップで順番が崩れると決定性が壊れるため。
5. **ロックステップのサービスは 0 ステップで完了する**（段 H の実装で決めた、2026-11-26）。1 つの要求で 1 つの箱庭のステップを進め、そのステップのうちに応答するので、`on_step` が「まだ」を返したら誤りとして止める。何ステップもかかる処理は、非同期のサービスで書く。

**分担**

```text
共通ルート（ランナー）
  ステップの門（共通機能）
    ・lockstep: true の入力が登録されていれば、1 ステップを始める前に、全員に「来ている？」と聞く
    ・全員そろうまで始めない（物理も箱庭の時刻も進めない）
    ・タイムアウト（最初と 2 回目以降）、一時停止、来なかった入力の名前を出して止める
          │ 口：「このステップの入力は来ているか」（今の ILockstepInput の lockstep_ready() にあたる）
          ▼
非同期 RPC のコア
  サービスの受け口（Source）がこの口も実装する
    ・core-pro を見て、このステップの要求が来ていれば取っておき、「来ている」と答える
    ・ステップの中（command source の段）では、取っておいた要求で on_request を呼ぶ（core-pro を二重に poll しない）
```

呼ぶ順（アセットのドライバのループ、`hakoniwa_asset_driver.cpp`）：

```text
① ランナーの「進めてよいか」→ ステップの門 → 登録された入力の「来ているか」
     そろっていなければ ① に戻る（②③ は呼ばない）
② ランナーの 1 ステップ → ActuatorRuntime：command source → controller → arbiter → plant → publish
③ 箱庭の時刻を進める
```

| 誰が持つか | もの |
|---|---|
| 共通ルート（ステップの門） | そろうまで待つ、タイムアウト（最初と 2 回目以降で別の長さ。旧ルートと同じ）、一時停止の間は進めず時計も止める、来なかった入力の名前を出して止める |
| 非同期 RPC のコア（受け口） | このステップの要求を core-pro から取っておき「来ているか」に答える、1 ステップに 1 要求（応答の前に次が来たら誤り。決まり 4） |

- ステップ番号の確かめ（旧ルートの飛び・重複・逆戻りの検出）は、番号が要求の中身（型ごと）にあるので、コアからは見えない。「1 ステップに 1 要求」で重複と飛びはほぼ防げる。それでも番号を確かめたいサービスは、`on_request` で断る。
- ロックステップの切り替え（`HAKONIWA_ROBOT_RUNTIME_ENABLE_LOCKSTEP`）が入っていないビルドでは、`lockstep: true` のサービスは組み立てのときに断る。
- 段 H の実装（`AsyncServiceLockstepGate`）は、タイムアウト・一時停止・待つことを自分で持っている。これを共通ルートの門に移し、受け口には「来ているか」だけを残す（段 H2、第 7 節）。

**口は共通、実装は入力ごと（PDU 版も残す）**（2026-11-26 決定）

「このステップの入力は来ているか」の口は、今の `runner::ILockstepInput`（`lockstep_ready()`）がそれにあたる。口は共通ルートに**残す**（名前は見直してよい）。口を実装すれば、どんな入力でも同じ門でロックステップに参加できる。**RPC のロボットも pub/sub のロボットも、同じ門で待てる**（混ぜてもよい）。今の実装は 3 つ：

| 実装 | どうするか |
|---|---|
| 旧ルートの RPC（`AsyncRpcInput`） | 車と人の移植（段 P1〜P3）でサービスの受け口へ。段 J で消える |
| PDU の車の入力（`AckermannDrivePduEventReader`） | **残す**（pub/sub のロボットのためのロックステップの入力）。CARLA 比較 P0 の車もこの入力で動いており、今回は移さない（2026-11-26 決定）。RPC に移すかは次以降 |
| Float64 の PDU 入力（タイヤの摩擦など） | **残す**（同上）。debris-highway の摩擦（`vehicle_input: rpc` の車）は、車のサービスの要求の `tire_friction` に移す（段 J2）。P0 の摩擦は PDU のまま |

**pub/sub のロックステップの決まり**（PDU 版の入力を使うとき）：書く側は、**初期化のときに 1 回、そのあと毎ステップ必ず書く**。値が変わったときだけ書く入力は、ロックステップの入力にしてはいけない（`lockstep_input.hpp` のコメントにある決まり）。受信の印の取り違えや、書く側の初期化と待つ側の登録の競合など、落とし穴が多かったので、決定性が大事な使い方では、交互に投げ合う RPC のロックステップ（決まり 1〜5）を勧める。この決まりはマニフェストと手順の説明にも書く。
