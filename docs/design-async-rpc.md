# 非同期 RPC の設計（メモ）

- 作成：2026-11-16
- 状態：設計の方針。段 A を実装済み（2026-11-16）

## 1. 目的と方針

robot-runtime に、外の人がプラグインとして RPC サービス（「この関節角へ動かして、着いたら返して」「今の状態を返して」など）を足せるようにする。

方針は一つ：**RPC のセッション管理は hakoniwa-core-pro に任せ、robot-runtime 本体には持たない。**

- 要求の受付、キャンセルの受付、状態（DOING・CANCELING・DONE）、進捗、結果コードは、core-pro の RPC サービスがすでに共有メモリの上で持っている。
- タイムアウトの監視はクライアントの責務（core-pro の決まり）。サーバ（robot-runtime の側）は時間を数えない。
- キャンセルが来たときにどうするか（その場で止まる、減速して止まる、途中の姿勢を保つ など）は、サーバのプログラム、つまりプラグインが決める。robot-runtime はキャンセルの到着をプラグインのフックに渡すだけで、その結果は core-pro の仕組み（結果コード CANCELED の応答）で返す。

こうすると、robot-runtime 本体の仕事は「サービスの準備」と「毎ステップ、決まった順にプラグインのフックを呼ぶこと」だけになる。

もう一つ：**サービスは、今ある 1 ステップのパイプラインに、今ある型を継承した部品として乗せる。** ランナーの横に別の入力を置かない。共通の処理に「サービスなら」「ロックステップなら」の分岐を入れない（第 3.1 節）。

## 2. 今あるもの（2026-10-27、Urban の車と人のため）

| 部分 | 中身 |
|---|---|
| サービスの準備 | アセットの登録の直後に、Runner が `hako_asset_service_initialize(サービス定義)` を呼ぶ。各サービスのサーバは、そのあと `hako_asset_service_server_create` で作る |
| 汎用の通り道 | `IAsyncRpcChannel`（実体は `CoreAsyncRpcServiceChannel`）。`poll` で要求を受け取り、`reply` で応答を返す。中身は「ステップ番号 + 型を決めないデータ」 |
| ステップとの合わせ方 | `AsyncRpcInput`。物理の前に要求を指令に変えるフック（apply）、物理の後に応答を作るフック（build_response） |
| 使っている例 | 車 `CarService/AckermannStep/<車>`、人 `PersonService/PersonStep/<人>` |
| サービス定義を作る道具 | `tools/gen_rpc_service_config.py`（サービス定義の JSON と起動の引数） |
| ビルドの切り替え | `HAKO_ENABLE_ASYNC_RPC_INPUT`。有効にしているのは Urban のビルドだけ |

足りないもの：

1. 型ごとのフックが本体に組み込まれている（車と人）。外から足す口がない。
2. 待ち方がロックステップだけ。全ロボットからステップ k の要求がそろうまで物理を進めない。「要求が来たら答え、来なくてもステップは進める」形がない。
3. キャンセルを誤りとして扱っている。`poll` が `REQUEST_CANCEL` を受けると、誤りとして止まる。
4. サービス定義の道具が、車と人の 2 種類の型しか知らない。

## 3. 責務の分担

| 担い手 | 持つもの | 持たないもの |
|---|---|---|
| hakoniwa-core-pro | 要求・応答の受け渡し、キャンセルの受付、状態、進捗、結果コード | ロボットの意味 |
| クライアント（外のアセット、コントローラ、シナリオ） | 要求を出す、タイムアウトを監視する、必要ならキャンセルを出す | ロボットの内部 |
| robot-runtime 本体 | サービス定義の読み込み、サーバの作成、毎ステップのフックの呼び出し、イベント（要求・キャンセル）をフックへ渡す、フックの結果を core-pro の API へ渡す | セッションの状態、タイムアウト、キャンセル後の振る舞い |
| プラグイン | 要求の中身の解釈、指令の作成、完了の判断、キャンセルされたときの振る舞い、応答の中身 | 共有メモリ、サービスの準備 |

### 3.1 1 ステップの中の置き場所（基礎設計）

robot-runtime の 1 ステップは `ActuatorRuntime::step()` が回す。MuJoCo の step は、この中のプラントで 1 回だけ呼ぶ。

```text
状態を読む → command source → controller → arbiter → plant（MuJoCo step）→ sensor → publish
```

今のパイプラインは pub/sub の形をしている。指令の入口（command source）が新しい入力を受け、コントローラが指令に変え、Arbiter が選び、プラントが進め、publisher が状態を出す。非同期のサービスも同じ形に乗る。

```text
状態を読む
→ command source … サービスの受け口：core-pro を poll。要求・キャンセルを入力にする
→ controller     … 要求なら on_request、キャンセルなら on_cancel。処理中なら on_step（指令と完了か）
→ arbiter        … 今のまま
→ plant          … 今のまま（MuJoCo の step はここだけ）
→ sensor         … 今のまま
→ publish        … 完了していたら応答を送る
```

| 段 | 今ある型 | サービスの部品（robot-runtime が持つ） | すること |
|---|---|---|---|
| command source | `ICommandSource` | サービスの受け口 | core-pro のサーバを service_id で `poll` する。要求（バイト列のまま）かキャンセルを、コントローラへの入力にする。何も来ていなければ入力なし |
| controller | `IController` | サービスのコントローラ | 入力が要求なら `on_request`（断られたら INVALID の応答を予約）、キャンセルなら CANCELING にして `on_cancel`。処理中なら毎ステップ `on_step(状態, 時刻)` を呼び、指令と完了かを受け取る。待機中は指令を出さない（Arbiter に選ばれない） |
| arbiter・plant・sensor | 今のまま | 変えない | |
| publish | `IStatePublisher` | サービスの応答 | 完了していたら、物理の後に応答を送り（状態 DONE と結果コード）、待機に戻す |

- 3 つの部品は、1 つのサービス（`IAsyncService`）と、そのサービスの core-pro のサーバ（service_id）を共有する。ユーザが書くのは `IAsyncService` だけ。プラグインになっても同じ（第 5 節）。
- 部品は今ある型を継承するだけで、パイプラインの本体（`ActuatorRuntime`）にはサービスのための分岐を入れない。組み立ては工場（factory）が、今の車の受け口やコントローラと同じようにする。
- コントローラは、入力のないステップにも毎回 `update` が呼ばれる（今の決まり）。だから処理中の `on_step` を毎ステップ呼べる。
- 応答を publish の段で送るので、物理の後の状態（着いた位置など）を応答に入れられる。
- core-pro のサーバの呼び出し（`server_create`・`poll`・`get_request`・`get_response_buffer`・`put_response`）は、service_id で呼ぶ小さな窓口 1 つにまとめる。テストでは偽物に替える。
- 旧ルート（`AsyncRpcInput`）は、ランナーに専用の呼び出し（要求を当てる・応答を返す）を持っている。新ルートは持たない。

**2 つの速さ（2026-11-16 決定）**：外とのデータのやり取りは箱庭のステップで、制御と物理は物理のステップで動く。

| 速さ | 段 | すること |
|---|---|---|
| 箱庭のステップ（境目に 1 回） | command source | 外からの入力を受ける（PDU、RPC の要求とキャンセル） |
| 物理のステップ（刻みごと） | controller → arbiter → plant → sensor | 制御、選択、物理、センサの読み取り |
| 箱庭のステップ（境目に 1 回） | publish | 外へ出す（状態、センサの値、RPC の応答） |

- 背景：今まではおもに pub/sub で、箱庭のステップと物理のステップが同じだったので、違いが見えなかった。旧ルートで、外（シナリオ）が 10 ms ごとに要求を投げてくる一方、物理は 1 ms で刻む（`physics_substeps`）ことが分かり、2 つの速さを分ける必要が出た。
- 今の作りは、command source を物理の刻みごとに `poll` する。外のアセットは別のプロセスで書き込むので、要求が刻みの何回目で見えるかが実時間で変わり、結果が決まらない。外の時刻が進むのは箱庭のステップの境目だけなので、入力もそこでだけ受ける。
- サービスでは、要求とキャンセルを境目で受け、`on_step` は刻みごとに呼び（細かく制御できる）、応答は境目で返す。刻みの途中で完了したら、その刻みから `on_step` を呼ばず指令も出さない（残りの刻みはほかのコントローラが選ばれる）。応答は境目で送る。
- 刻みが 1 なら、全部が毎ステップ 1 回で、今と同じ。
- これは共通の土台の直し：`ActuatorRuntime::step()` に、今の「出力するか」（`publish`）に並べて「入力を受けるか」を足し、ランナーは最初の刻みだけ受ける（段 B0）。

### 3.2 コントローラが見るのは観測と推定（2026-11-16 決定）

サービスの `on_step` に真の値を渡すと、サービスのコードが「真の値が見える」前提で書かれ、推定（EKF）を入れるときに書き直しになる。これはサービスだけでなく、コントローラ全員に共通の話なので、共通の土台を直す。

今の作り（コードで確かめた）：

- コントローラは全員、ステップの頭でプラントから読んだ真の値（関節、剛体）を見ている（`ActuatorRuntime::step` の 1）。
- センサの段（`ISensorStage`、`MujocoSensorStage`）は物理の後で真の値からセンサの値を作り `RobotState::sensor_readings` に書くが、使うのは publish だけで、コントローラには届かない。
- 推定の考え方はない。コントローラのプラグインの関節の状態の出どころ「観測値」（`PluginJointStateSource::Observed`）は TODO で、選ぶと断られる。
- お手本は Drone PRO：`IStateEstimator`（センサの値と、記録用の真の値を入れ、推定値と「準備ができたか」を出す）。順は 真の値 → センサ → EKF → 制御 → 物理。Control Link の仕様も「制御に入るのは観測できる値で、真の値ではない」。

決めた形：

```text
（前の物理の後）プラント → センサの段（今ある）→ 推定の段（新しい）
                                         ↓ 「コントローラが見る状態」を作って持つ
（このステップ）入口 → コントローラ（全員。サービスの on_step も）→ Arbiter → プラント …
```

- **推定の窓口**は Drone PRO の `IStateEstimator` と同じ形：入力はセンサの値・時刻・真の値（真の値は記録と簡略版のためだけ）、出力は推定値（関節の位置・速度、剛体の位置・姿勢・速度）と「準備ができたか」。今回は**真の値をそのまま返す簡略版**だけを入れる。
- **コントローラが見る状態**は、推定の段のあとで推定値とセンサの値から作り、次の刻みのコントローラに渡す。形は今の `RobotState` のまま（関節と剛体の欄に推定値、センサの値の欄にセンサの値）。だから**コントローラの関数の形は変わらない**。組み込み、プラグイン、サービスのどれも書き直さず、中身だけが観測できるものになる。プラグインの「観測値」の TODO もこれで埋まる。
- 簡略版は真の値を返すので、切り替えの ON と OFF で結果がビット単位で同じになるはず。それを確かめのテストにする。
- 座標は NWU（世界）・FLU（センサ）。四元数の並びは sensor adapter が wxyz、`RobotState` の剛体が xyzw なので、境目ごとに明記する。
- C の境目（段 E）では、推定値の関節を今の `HakoJointStatesV1` で渡す。剛体の推定値とセンサの値の C の型は段 E で足す。

### 3.3 切り替え（ifdef）

新ルート（サービス）、2 つの速さ（第 3.1 節）、観測と推定（第 3.2 節）の 3 つは、**同じ切り替え一つ**に入れて main にマージする：`HAKONIWA_ROBOT_RUNTIME_ENABLE_ASYNC_SERVICE`（名前は仮）。OFF なら今の振る舞い（入力は刻みごと、コントローラは真の値、サービスなし）。マージ済みの段 A の変更（キャンセルをイベントにする、結果コード）も、次の PR でこの切り替えの中に入れる（OFF なら止まるときの理由の文言も前のまま）。

## 4. サービスの持ち方（core-pro のサービスのモデル）

### 4.1 core-pro が持つもの

| もの | 中身 |
|---|---|
| サービス定義（`service.json`） | サービスごとに、名前（例 `Service/Add`）、型（例 `hako_srv_msgs/AddTwoInts`。要求と応答の PDU の型が決まる）、`maxClients`、PDU の大きさ（サーバ側とクライアント側の `baseSize`・`heapSize`）。`hako_asset_service_initialize` が読み込み、共有メモリにサービスの表を作る |
| service_id | `hako_asset_service_server_create(アセット名, サービス名)` が返すサービスの表の番号。サーバ側の API はすべてこの番号で呼ぶ |
| client_id | クライアントが `hako_asset_service_client_create(アセット名, サービス名, クライアント名)` でつながるたびに 0 から振られる。クライアントごとに要求用と応答用の PDU チャネルを持つ |
| 状態 | クライアントごとに IDLE・DOING・CANCELING。結果コード（OK・ERROR・CANCELED・INVALID・BUSY）、進捗も持つ |
| 実行のまたぎ | サーバのオブジェクトは実行をまたいで残る。新しい実行が始まると core-pro が状態を戻す（core-pro #109）。robot-runtime はリセットしない |

### 4.2 1 サービス 1 クライアント

core-pro は 1 つのサービスに複数のクライアントを定義できる（`maxClients`）。ただしサーバ側は「今のクライアント」（`current_client_id`）を 1 つだけ見て順に回す作りで、要求のヘッダと中身を入れる場所がサービスに 1 つしかない。複数のクライアントが同時に要求すると取り違えうる。

今回は **1 サービス 1 クライアント**（`maxClients: 1`）とする。同じ型のサービスでも、クライアントごとに別のサービス名にする（車の `CarService/AckermannStep/<車>` と同じ形）。`maxClients` が 1 でない定義は、起動時に止める。

### 4.3 robot-runtime が知っておく情報

robot-runtime が持つのは「サービス名と型」（定義から）と「service_id」（作ったときに受け取る）だけ。ほかの状態は毎回 core-pro に聞く。

| 情報 | どこから | 何に使う |
|---|---|---|
| サービス名 | プラグインの `describe` → サービス定義 | `server_create`、ログ |
| 型（要求・応答の PDU） | 同上 | 要求を解く・応答を作る（中身の変換はプラグイン） |
| PDU の大きさ | サービス定義 | 応答の入れ物の確認 |
| `maxClients` | サービス定義 | 1 以外なら起動時に止める |
| service_id | `server_create` の戻り値 | `poll`、`get_request`、`get_response_buffer`、`put_response`、`set_progress`、`server_status` |
| 今のクライアント（client_id） | `server_get_current_client_id` | ログ・診断（1 クライアントなら常に 0） |
| 状態（IDLE・DOING・CANCELING） | `server_status` | プラグインに進行中の要求があるかを渡す |

## 5. プラグインの形

### 5.1 分担

定型の処理はすべて robot-runtime が持ち、プラグイン（ユーザ）は「要求の中身の解釈」「プラントへの指示」「完了の判断」だけを書く。

| robot-runtime が持つ | プラグインが持つ |
|---|---|
| `poll`、要求の取り出し（`get_request`）、キャンセルの受け付け、応答の入れ物の確保と送信（`get_response_buffer`・`put_response`、状態と結果コード）、進捗の送信（`set_progress`） | 要求のバイト列を自分の型に変換する、中身を確かめる、プラントへの指示を出す、完了（または止め終わり）を判断する、応答の中身を作る |

プラグインに渡すのは service_id と要求のバイト列だけで、ステップ番号のような旧ルートの考え方は持ち込まない。

### 5.2 境目は C

- C の型と関数だけが境目を越える（コントローラのプラグイン、外部センサプラグインと同じ決まり）。robot-runtime とプラグインを、違うコンパイラや違うビルド設定で作っても壊れないようにするため。C++ の抽象クラスは、コンパイラが違うとメモリの並びが合わないことがある。
- 要求は「service_id、サービス名、型の名前、PDU のバイト列」で渡す。プラグインは service_id（またはサービス名）を見て自分のものなら、生成済みの変換関数（`pdu_cpptype_conv_*`）で自分の C++ の型に変換する。応答も、プラグインが自分の型からバイト列に変換して返す。
- プラグインの中で抽象クラスの書き味にしたいときのために、C の境目の上に薄い C++ のヘッダを用意してもよい（プラグインの中だけで閉じる）。

### 5.3 フック

| フック | いつ | プラグインがすること | 返すもの |
|---|---|---|---|
| `describe` | 読み込み時 | 提供するサービス名と、要求・応答の型を返す | サービスの一覧（サービス定義を作る道具が使う） |
| `on_request(service_id, 要求)` | 受け口が `REQUEST_IN` を受けたステップの、controller の段（物理の前） | 要求を自分の型に変換し、中身を確かめ、受け付けるならプラントへの指示を始める | 受け付けた／受け付けない（受け付けないなら robot-runtime が結果コード INVALID で応答する） |
| `on_step(service_id, 状態, 時刻)` | 進行中の要求があるサービスについて、毎ステップ controller の段（物理の前。前のステップの物理の後の状態を見る）。状態は core-pro のサーバの状態そのまま（DOING＝処理中、CANCELING＝キャンセル中） | プラントの状態を見て、指示を続ける。CANCELING なら止め方に切り替える。完了か（キャンセル中なら止め終わったか）を判断する | まだ／完了（OK と応答の中身）／止め終わった（CANCELED と応答の中身）／失敗（ERROR）。任意で進捗 |
| `on_cancel(service_id)`（任意） | 受け口が `REQUEST_CANCEL` を受けたステップの、controller の段 | キャンセルが来たことの通知だけ。記録やログなど、来た瞬間を知りたいプラグイン向け。実装しなくてよい | なし |
| `reset`、`destroy` | リセット、終了 | 進行中の要求とプラントへの指示を捨てる | なし |

- `on_step` は指令と「完了か」を 1 回で返す。「完了」か「止め終わった」を返すと、そのステップの publish の段（物理の後）で応答を送る（状態 DONE、結果コード OK か CANCELED）。
- 通知と処理を分ける：`on_cancel` は通知だけで、それ以上でもそれ以下でもない。キャンセルの処理（止め方の切り替え、止め終わりの判断）はすべて `on_step` でする。`on_cancel` を書かないプラグインも、`on_step` の状態だけで正しく動く。
- 指令は、アクチュエータを直接は触らず、サービスのコントローラの出力として Arbiter に出す。最後の選択（Arbiter）と安全の検査（範囲、期限、有限の値）は、今までどおり robot-runtime が持つ。状態は読み取りだけ。
- フックはシミュレーションのスレッドで、ステップの間に呼ばれる。プラグインは待たずにすぐ戻る。

### 5.4 core-pro が保証していること

core-pro のサーバは、要求の受け付けを状態で管理している（`hako_service_protocol_server.cpp` の `poll`）。

| サーバの状態 | 要求が来た | キャンセルが来た |
|---|---|---|
| IDLE（処理していない） | サーバに届く（`REQUEST_IN`）。状態は DOING に | 警告を出して捨てる |
| DOING（処理中） | core-pro が BUSY で応答し、サーバには届けない | サーバに届く（`REQUEST_CANCEL`）。状態は CANCELING に |
| CANCELING（キャンセル中） | core-pro が BUSY で応答する | 同上（BUSY） |

このため、`on_request` は処理していないときにしか来ない。処理中に同じサービスから来た要求を robot-runtime が弾く必要はない。

### 5.5 プラントの隠し方と Arbiter（今ある仕組みに乗る）

プラグインには MuJoCo を見せない。robot-runtime はすでに、物理エンジンに依存しない形でプラントと状態を持っている。

| 仕組み | 今ある形 | サービスのプラグインでの使い方 |
|---|---|---|
| プラント | `IActuatorPlant`（MuJoCo は実装の 1 つ `MujocoActuatorPlant`）。本体は「状態を読む」「指令を渡して 1 ステップ進める」だけを知る | プラグインはプラントに直接触らない |
| 状態 | `RobotState`：関節ごとの `ActuatorState`（名前、位置、速度、トルク）、剛体ごとの `BodyState`（名前、位置、姿勢、並進・角速度）、センサの読み | C の境目では、コントローラのプラグインと同じ `HakoJointStatesV1` で関節の状態を渡す。剛体の状態の C の構造体は、要るときに足す |
| 指令 | `ActuatorCommand`（関節、種類、値、期限） | `HakoJointCommandsV1` で返す |
| 時刻 | `HakoTickV1`（シミュレーション時刻、ステップ番号、前のステップで自分の指令が選ばれたか `selected`） | そのまま渡す。`selected` で、自分の指令が実際にプラントへ行ったかを確かめられる |
| Arbiter | `PriorityCommandArbiter`：指令を出せる状態のコントローラのうち、優先度の一番高いものを選ぶ。入力待ちのものは選ばれない | サービスのプラグインを、優先度付きの「コントローラの 1 つ」として載せる。要求を処理している間だけ指令を出し、処理していないときは入力待ち。何もしていないときは保持などのコントローラが選ばれる |
| 安全の検査 | プラントの入口で、種類・期限・有限の値・範囲を確かめる | 変えない |
| プラグインの共通ヘッダ | `HakoPluginHeaderV1` に種類（`kind`）の欄がある | 種類「サービス」を足す。読み込みはコントローラのプラグインの仕組みをそのまま使う |

新しく作るのは「サービスの関数表」と、第 3.1 節の 3 つの部品（受け口・コントローラ・応答）だけ。

## 6. 待ち方

本体の待ち方は一つ：**非同期**。要求が来ていなくてもステップは進む。要求は箱庭のステップの境目で受け、応答はプラグインが完了と判断した箱庭のステップの境目で返す。robot-runtime は要求の到着を待たないので、時間を数える必要もなく、タイムアウトはクライアントだけが持つ。

ステップを止めたいサービスのために、本体は**任意のフックを一つ**だけ持つ：「まだ進めないで」（ランナーの今の「進めてよいか」の確認 `ready_to_step` に、サービスの返事を足す）。待つ条件はプラグインが決める。

| 例 | 待ち方 |
|---|---|
| アームの移動の指令（完了で返す）、状態の問い合わせ（その場で返す） | 非同期。フックは使わない |
| CARLA 比較の車（`AckermannStep`）と人（`PersonStep`） | フックを使うプラグイン。「全台のステップ k の要求がそろうまで進めない」「ステップ番号の飛び・重複・逆戻りで止める」「タイムアウト」は、すべてプラグインの中に持つ |

- 今のロックステップの車 RPC は、CARLA 比較の検証のための特殊な実装で、本体の機能ではない。「ユーザがこう選び、こう設計・実装した」というプラグインの例として作り直す。
- 混ぜてよい。「進めないで」と言うサービスがあれば、ステップはそこで待ち、その間は非同期のサービスにも新しい要求は届かない（入力は境目でしか受けない）。混ぜて困る組み方をしないのはユーザの責任。
- **一本にする。** 同じような RPC のルートが 2 つあるのはよくない。CARLA 比較の車と人をプラグインとして作り直し、今までの結合テストと Urban の決定性（ステップの記録が同じになること）で振る舞いが変わらないことを確かめてから、旧ルート（`AsyncRpcInput`）を消す（第 7 節の段 H〜J）。

### 6.1 Arbiter の束ね方はユーザが決める

Arbiter の決まり（優先度の一番高いグループを丸ごと選ぶ）は変えない。どう束ねるか（車ごとに分けるか、まとめるか）はユーザが決める。robot-runtime は、すべてのコントローラ（車、サービスを含む）の優先度とグループを、アセットのマニフェストで書けるようにするだけ。

- 今は車（Ackermann）のコントローラの優先度とグループがコードに書き込まれている（優先度 10、グループ `ackermann-pdu-direct`）。マニフェストで変えられるようにし、今の値は書かなかったときの既定値として残す（段 C）。コントローラのプラグインの `priority` に合わせる。
- 例：全台のサービスと車の指令を同じグループに入れると、関節が重ならない出力がまとめて選ばれる。同じ車に 2 つの指令（サービスと、ふだんの指令）を同時に出さないのはユーザの責任（重なれば Arbiter は何も選ばない）。

## 7. 段階

一度に全部はやらない。易しい順に、各段で確かめてから次へ。今の車と人（ロックステップ）の振る舞いは、どの段でも変えない。

| 段 | 内容 | 確かめ方 |
|---|---|---|
| A（済み） | **キャンセルを誤りにしない**：core-pro の口の包み（旧ルートと共通）が、キャンセルをイベントとして返し、応答に結果コードを持たせる。次の PR で切り替え（第 3.3 節）の中に入れる | 単体テストと、本物の core-pro でのキャンセルの結合テスト |
| B0 | **共通の土台：2 つの速さ**：`ActuatorRuntime::step()` に「入力を受けるか」を足し、ランナーは箱庭のステップの最初の刻みだけ command source を `poll` する（出力は今どおり最後の刻みだけ） | 刻み 4 で、source が箱庭のステップに 1 回だけ呼ばれ、controller・plant は 4 回。今の全テスト（車の PDU・RPC、人、刻みのテスト）と、Urban の決定性（同じ入力でステップの記録が同じ） |
| B1 | **共通の土台：観測と推定**（第 3.2 節）：推定の窓口と、真の値を返す簡略版。推定の段のあとで「コントローラが見る状態」を作り、次の刻みのコントローラに渡す | 切り替え ON と OFF で、今の全テストの結果と Urban のステップの記録がビット単位で同じ。偽の推定（真の値をずらす）を入れると、コントローラが見る値がずれる（真の値ではなく推定値を見ている証拠） |
| B | **サービスの部品**：`IAsyncService`、core-pro のサーバの窓口、受け口（`ICommandSource` を継承）、コントローラ（`IController` を継承）、応答（`IStatePublisher` を継承） | 偽の窓口・偽のサービス・偽のプラントで、本物の `ActuatorRuntime` と `PriorityCommandArbiter` を回す。要求なしでステップが進む。要求はそのステップで渡る。処理中はサービスの指令が選ばれ、待機中は低い優先度の指令が選ばれる。完了したステップの物理の後に応答が出る。キャンセル、断り、ERROR、リセット |
| C | **車のサービス**（あわせて、車のコントローラの優先度とグループをマニフェストで書けるようにする。第 6.1 節）：`AckermannStep` の型を読み替える。要求の `step` は走るステップ数 N、`drive` はその間の指令。N ステップ走ったら OK で返し、応答の `pose`・`twist`・`sim_time_usec` はそのときの車の状態。キャンセルされたら速度 0 に切り替え、止まりきったら CANCELED。速度・操舵から車輪の関節の指令への変換は、今の車のコントローラのものを使う | 偽の状態での単体テスト |
| D | **組み立てとクライアントのサンプル**：工場とランナーで車のサービスを組み立て、Urban の車で動かす。core-pro のクライアントで呼ぶサンプル（`tests/integration/`） | サンプルから 3 通り：完了（OK）、キャンセル（CANCELED）、処理中の 2 つ目（core-pro が BUSY）。タイムアウトからキャンセルに進む流れも |
| E | **プラグインの C の境目**：`HakoPluginHeaderV1` の種類「サービス」、関数表。C の関数表を `IAsyncService` に見せる包み。車のサービスをプラグインに移す | C だけで書いた偽のプラグインの契約テスト。D のサンプルで同じ結果になる |
| F | **サービス定義の道具**：プラグインの `describe` から、サービス定義の JSON（`maxClients: 1`）を作る | 手で書いたものと同じになる |
| G | **ロボットアームで有効にする**：SO-101 で「関節の目標へ動かし、着いたら返す」 | 外のクライアントから頼み、完了とキャンセルが返る |
| H | **「まだ進めないで」のフック**：サービスがステップを止められる任意のフック | 偽のサービスが止めている間、箱庭の時刻が進まない。止めるのをやめると進む |
| I | **CARLA 比較の車と人を、例のプラグインとして作り直す**：全員の要求待ち、ステップ番号の確かめ、タイムアウトをプラグインの中に | 車と人の結合テストと、Urban の決定性（ステップの記録が同じ） |
| J | **旧ルートを消す**：`AsyncRpcInput` と専用の呼び出し | すべてのテストが通る |

先に端から端まで一本通し（B〜D）、プラグインの C の境目はそのあとに作る。クライアント側の書き味を見てから、プラグインの形を決めるため。試験台は Urban の車。

各段は、テストを先に書き（その時点では落ちる）、そのテストが通るように実装する。
