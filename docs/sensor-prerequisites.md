# センサ統合：全体像とフェーズ

Robot Runtime にセンサを統合する計画です。全体像を描いてフェーズに分け、簡単なものから 1 つずつ実証します。実証が通らなければ立ち止まり、通れば次のフェーズに進みます。

## 1. 全体像

```text
入力 → コントローラ → arbiter → actuator（plant.step） → sensor → publisher
```

- **sensor 段**は物理を 1 回進めるたびに、MuJoCo から真値を取り出し、センサの実装（アダプタ）に渡して測定値を得ます。
- **publisher** は、既存の出力と同じ仕組みで測定値を送ります。
- 実装は `hakoniwa` / `gazebo` / `airsim` から、センサごとに選べます。起動時に、実装一覧（`catalog/sensor-implementations.json`）と照合します。
- センサの定義ファイルは、どの実装でも共通の JSON です。
- センサを使うアプリケーションだけが、センサ機能を有効にし、実装のライブラリをリンクします。

取り付け方はセンサ種別ごとに違います。

| 種別 | 何に付けるか | MJCF に必要なもの |
|---|---|---|
| エンコーダ・関節トルク | 既存の関節 | 何も足さない（関節名で指定） |
| 力覚 | 2 つの剛体の切れ目（ロボットと工具の間） | 工具側が独立した body であること、センサ原点の site |
| IMU | 剛体の上の 1 点 | site |
| 地磁気・気圧・GPS | 剛体の上の 1 点 | site と、世界の地理的な基準点 |
| 測距・LiDAR・カメラ | 剛体の上の 1 点と向き | site と、ロボット自身に当たらない除外設定 |

## 2. フェーズ

| フェーズ | 内容 | 実証（これが通れば次へ） |
|---|---|---|
| **1. エンコーダ** | hakoniwa 実装、SO-101 の 6 関節、角度と角速度、測定値を JointState で送る | 下の 2.1 |
| 2. 関節トルク | 関節を通る伝達トルクを足す | フェーズ 2 の開始時に決める |
| 3. 力覚 | SO-101 の手首（`wrist` と `gripper` の境目）に取り付け、WrenchStamped で出す | 下の 2.5 |
| 4. IMU | site に取り付け | 同上 |
| 5. gazebo 実装の選択 | 共通 JSON から Gazebo の設定への変換。同じアームで実装を替えて比べる | 同上 |
| 6. 測定値を制御に使う | コントローラ、サーボのモデル | 同上 |
| 後回し | 測距・LiDAR・カメラ、地磁気・気圧・GPS | — |

### 2.1 フェーズ 1：エンコーダ

前提：

| 項目 | 内容 |
|---|---|
| 取り付け | 関節名で指定する。1 自由度の関節（hinge / slide）でなければ起動時にエラー |
| 真値 | 角度と角速度（関節の位置と速度）。トルクは扱わない |
| 時刻 | 物理を 1 回進めるたびに測る。周期は物理ステップに丸める |
| 出力 | JointState。真値の出力と区別できる名前にする |
| 制御 | 測って送るだけ。コントローラは今のまま |

実証の項目：

1. 誤差なしの設定で、測定値が真値と一致する。
2. STS3215 の設定（12 bit）で、測定値と真値の差が分解能（2π/4096 rad）の範囲に入る。
3. 同じシードで 2 回動かすと、測定値の列が一致する。
4. 定義ファイルに未サポートの項目があると、起動しない。
5. SO-101 のつかんで置く動作の間、測定値の JointState が PDU で受け取れる。

### 2.2 設定仕様（センサ種別に依存しない）

センサの定義は、種別によらず次の 3 つだけです。出力は publisher 側で別に定義します。

1. **何のセンサか**：`name`、`type`、`implementation`
2. **MJCF の何に、どの位置と姿勢で付けるか**：`mount`
3. **センサ仕様（ノイズなど）**：`definition`（共通の定義ファイルへの参照）

スキーマ：

- センサ：`schemas/components/sensor-instances.schema.json`
- 出力：`schemas/components/sensor-output.schema.json`

センサの例：

```json
{
  "$schema": "https://hakoniwa.dev/schemas/sensor-instances.schema.json",
  "schema_version": 1,
  "sensors": [
    {
      "name": "shoulder_pan_encoder",
      "type": "joint",
      "implementation": "hakoniwa",
      "mount": { "mjcf_joint": "shoulder_pan" },
      "definition": "../sensor-models/feetech_sts3215.json"
    },
    {
      "name": "wrist_ft",
      "type": "force_torque",
      "implementation": "hakoniwa",
      "mount": { "mjcf_body": "gripper", "position_m": [0, 0, 0.02],
                 "orientation_deg": { "roll": 0, "pitch": 0, "yaw": 0 } },
      "definition": "../sensor-models/onrobot_hex_e_qc.json"
    }
  ]
}
```

`mount` の書き方は 2 つです。センサ種別に合わない書き方は、スキーマでエラーになります。

| 書き方 | 使う種別 | 内容 |
|---|---|---|
| `mjcf_joint` | `joint` | 1 自由度の関節を測る。位置と姿勢はない |
| `mjcf_body` と `position_m`・`orientation_deg` | それ以外 | body に固定する。位置と姿勢は body 座標で表し、省略時は 0。センサ軸は FLU |

出力の例（6 関節をまとめて 1 つの JointState にする）：

```json
{
  "$schema": "https://hakoniwa.dev/schemas/sensor-output.schema.json",
  "schema_version": 1,
  "sensors": ["shoulder_pan_encoder", "shoulder_lift_encoder", "elbow_flex_encoder",
              "wrist_flex_encoder", "wrist_roll_encoder", "gripper_encoder"],
  "pdu_config": { "pdu_name": "joint_states_measured",
                  "message_type": "sensor_msgs/JointState", "update_rate_hz": 50.0 }
}
```

スキーマでは表せないため、起動時に検査する項目：

- 実装・種別・定義ファイルの項目・組み込み（実装一覧との照合）
- センサ名が Runtime 内で一意
- `mjcf_joint` が存在し、hinge か slide。`mjcf_body` が存在し、world ではない
- 出力の `sensors` の名前がすべて存在し、メッセージ型に合う種別（JointState なら `joint`）
- PDU 定義にチャンネルがあり、型が合う

その他：

- JointState の `name` には、センサが付いている MJCF の関節名を入れます。`position` と `velocity` に測定値を入れ、`effort` はフェーズ 1 では空にします。
- 乱数の系列は、全体のシード、ロボット名、センサ名から作ります。全体のシードは Runtime Config の `sensors.seed` に置き、省略時は 0 です。
- 出力のメッセージ型は、フェーズ 1 では `sensor_msgs/JointState` だけを許します。フェーズが進むたびに足します。

### 2.3 フェーズ 1 の実証結果（2026-11-11）

SO-101 の 6 関節にエンコーダを付け、Hakoniwa の上で標準デモと把持デモを流して確認しました。

| 項目 | 結果 |
|---|---|
| 1. 誤差なしで真値と一致 | 合格。530 時点、各関節が最大 1.35 rad 動く間、位置・速度の差が 0 |
| 2. STS3215（12 bit）で分解能の範囲 | 合格。位置の差の最大 7.664e-4 rad。分解能の半分（7.670e-4 rad）以内 |
| 3. 同じシードで同じ列 | 合格。ノイズ付き設定で 2 回動かし、3,018 サンプルで誤差の列が完全に一致。シードを変えると最大 2.1e-3 rad 違う |
| 4. 未サポートの項目で起動しない | 合格。8 種類の誤り（未サポート項目、綴り違い、未知の実装、関節センサを持たない実装、MJCF に無い関節、関節センサに body 用の取り付け、出力に無いセンサ名、PDU チャンネル無し）すべてで、原因を示して起動しない |
| 5. 把持デモの間、測定値が届く | 合格。42 秒間（手首は最大 4.8 rad 回転）、測定値の JointState が届き続け、誤差は分解能の半分以内 |

仕様（仮説）について分かったこと：

- センサの定義は「何のセンサか・どこに付けるか・定義ファイル」の 3 つで足りた。
- センサの実装は、時刻を 0 から物理ステップ単位で数える。Runtime の時刻はリセット後も 0 に戻らないことがあるため、sensor 段が自分で数えて、Runtime の時刻に換算する。
- 定義ファイルの先頭の `$schema` は、どの実装でも許す。
- Runtime の既存の読み込みは、知らない種類の部品を黙って読み飛ばしていた。センサ機能なしのビルドでセンサが書かれていたら、起動しないようにした。

- 実装名から実装を得る方法が、公開インタフェースに無かった（使う側が手書きのつなぎを書く必要があった）。hakoniwa-sensor-adapter に実装の名札（`SensorAdapterImplementation` と、実装名で決まる入口 `hako_sensor_adapter_implementation_<name>()`）を足した。Runtime は名札をそのまま登録し、アプリケーションのビルドは実装名の一覧から登録コードを生成する。
- 起動時に、実装一覧に書いた種別と、リンクした実装の名札が持つ種別の食い違いも検査する。
- 出力は ROS 2 と同じく `sensor_msgs/JointState`（ラジアン）。エンコーダのカウント値やフラグは JointState に欄がないので送らない。ドライバの層まで試したい用途が出たら、専用の型を足す。

残っていること：

- SO-101 のビルド設定と設定ファイルは hakoniwa-robot-arm の fork に置き、完成形にしてから本家へ PR を出す。

### 2.4 フェーズ 2：関節トルク（2026-11-11）

仮説：

- 設定は増やさない。関節センサの定義ファイルの `torque` 欄（測り方 `sensor` / `current`、レンジ、誤差、摩擦）で決まる。
- 真値は、関節を通って伝わるトルク（子の剛体の `cfrc_int` を関節の位置に移し、軸に投影したもの。親が子に及ぼす向き）。
- `mj_step` の直後は、力が 1 ステップ前の状態で計算されたままなので、トルクを測るセンサが 1 つでもあれば、ステップの後に `mj_forward` と `mj_rnePostConstraint` を 1 回だけ呼び、角度と同じ時刻の値にそろえる。
- 出力は同じ JointState の `effort`。1 つの出力のセンサは、全部トルクを測るか、全部測らないかにそろえる（混ざっていたら起動しない）。

実証（SO-101、Hakoniwa の上で標準デモと把持デモ）：

| 項目 | 結果 |
|---|---|
| 1. 静止状態で重力と一致 | 合格。401 時点で、記録した角度から質量と重心だけで独立に計算した重力トルクとの差は最大 1.2e-5 N·m（例：shoulder_lift −0.5388 N·m） |
| 2. 時刻がそろっている | 合格。同じモデルの Python 版で 2,000 ステップ比べ、Runtime と同じ方法は、新しく計算し直した値と完全に一致（差 0）。計算し直さないと、接触の瞬間などに最大 13.5 N·m ずれる。計算し直しても物理は変わらない（位置がビット単位で一致） |
| 3. 電流からの推定 | 合格。測定値は「最新の指令と、ステップ後の位置から出したアクチュエータ力 ＋ 摩擦」。真値の出力のアクチュエータ力は 1 ステップ前の位置で計算されたものなので、その差 kp·v·dt を補正すると、3,348 サンプルの中央値で 1.6e-12 N·m 以内。例外は 5 時点の 25 サンプル（最大 0.49 N·m）で、どれも速度が急に変わる所。サーボのダンピング項（kv × 1 ステップの速度変化）と考えられるが、2 ms 前後のサンプルが記録されていないため確認はしていない |
| 4. 再現性と検査 | 合格。トルクのノイズ付きで同じシードの 2 回は完全に一致（3,042 サンプル）、シードを変えると最大 0.26 N·m 違う。トルクを測るセンサと測らないセンサを 1 つの出力に混ぜると、理由を示して起動しない |
| 5. 把持デモ | 合格。キューブを持っている間、測定トルクから腕自身の重力トルクを引いた残りが、キューブ（30 g）の重さによるトルクとほぼ一致（shoulder_lift −0.060 対 −0.058〜−0.061 N·m、elbow −0.034〜−0.044 対 −0.037〜−0.041 N·m）。キューブの位置をグリッパー先端で近似したため、差は最大 1 割程度 |
| 6. 計算の増加 | SO-101 で 1 ステップ 12 µs → 23 µs（+11 µs）。物理ステップ 2 ms に対して 0.6 % |
| 物理への影響 | なし。Runtime 上でも、トルクを測る実行と測らない実行で、真値の軌跡が完全に一致（同じ到着タイミングの実行どうし、3,030 サンプル） |

分かったこと：

- 実時間で動かすと、軌道指令がどのステップで届くかで、軌跡が 2 通りに分かれる（今回の実行では最大 0.027 rad）。センサとは関係なく、比較は同じ到着タイミングの実行どうしで行う必要がある。
- 電流からの推定は「サーボが今の位置と最新の指令で出している力」で、実機のサーボと同じ時刻の値になっている。真値の出力にあるアクチュエータ力とは 1 ステップずれている。
- 外部センサプラグインのホスト側で、`mj_step` の直後に `mj_rnePostConstraint` だけを呼んで力を読むと、力やトルクが 1 ステップ古くなる。同じ方法を使っている箇所は別途直す。

### 2.5 フェーズ 3：力覚センサ（2026-11-11）

仮説：

- SO-101 の手首の回転関節で `wrist` につながる `gripper` body は、グリッパーの開閉用サーボと固定側の爪で、工具そのもの。手首と工具の切れ目はもうあり、MJCF の変更は要らない（前に「組み替えが要る」と書いたのは誤りだった）。
- 取り付けは body 用の書き方（`mjcf_body: gripper`、位置 [0, 0, 0]、姿勢 0）。姿勢は roll・pitch・yaw［度］で、R = Rz(yaw)·Ry(pitch)·Rx(roll)。
- 真値は、工具側（その body の部分木）がロボット側に及ぼす力とトルク。センサの軸で表し、トルクはセンサ原点まわり。時刻はフェーズ 2 と同じく、ステップの後に計算し直してそろえる。
- センサ本体の質量と厚みは入れない。
- 出力は `geometry_msgs/WrenchStamped`（PDU 登録集にある型）。1 つの出力に力覚センサ 1 つで、`frame_id` はセンサ名。出力の部品の種類名は、JointState 専用の `sensor_joint_state` から `sensor_output` に変え、型は `pdu_config.message_type` で決める。

実証（SO-101、Hakoniwa の上で標準デモと把持デモ）：

| 項目 | 結果 |
|---|---|
| 1. 静止状態で工具の重さと一致 | 合格。402 時点で、記録した角度から質量と重心だけで独立に計算した値との差は、力が最大 2.3e-5 N、トルクが最大 6.9e-7 N·m（力の大きさ 0.971 N ＝ 工具 0.099 kg の重さ） |
| 2. 時刻がそろっている | 合格。同じモデルの Python 版で、Runtime と同じ方法は新しく計算し直した値と完全に一致（差 0）。計算し直さないと、接触の瞬間などに最大 89.6 N ずれる |
| 3. 把持 | 合格。誤差なしの設定で、キューブを持っている間（123 時点）、世界座標に直した力から工具の重さを引いた残りの鉛直成分が平均 −0.2945 N（キューブの重さ −0.2943 N） |
| 4. OnRobot HEX-E の設定 | 静止中の力は分解能（xy 0.2 N、z 0.8 N）がノイズより粗いため一定値に丸まる。トルクのばらつきは、データシートのノイズ（σ0·√(B/B0)）と分解能から別に計算した値と合う（ty 0.0041 対 0.0038、tz 0.0015 対 0.0015、tx は平均が丸めの境目近くにずれていることを入れると 0.0050 対 0.0049〜0.0050）。平均のずれ自体（約 −0.003 N·m、クロストークと非線形と考えられる）は独立には確かめていない |
| 5. 再現性と検査 | 合格。静止状態（真値が完全に同じ）で、同じシードの 2 回は完全に一致（301 時点）、シードを変えると最大 1.6 N 違う。8 種類の誤り（力覚に関節用の取り付け、MJCF に無い body、world への取り付け、WrenchStamped の出力に関節センサ、WrenchStamped の出力に 2 つのセンサ、JointState の出力に力覚センサ、gazebo が対応しない項目、PDU チャンネル無し）すべてで、理由を示して起動しない |
| 6. 計算の増加 | フェーズ 2 と同じ計算し直し（+11 µs / ステップ）を使う。力覚センサが 1 つでもあれば 1 回だけ行う |

分かったこと：

- HEX-E の分解能では、30 g のキューブはほぼ見えない。キューブを持つと、鉛直方向の力はセンサの z 軸に乗り（約 −1.27 N）、z の分解能 0.8 N で −1.6 N に丸まる。そのため世界座標での増加は −0.58 N と、実際（−0.29 N）の約 2 倍に見える。誤差なしの測定値を HEX-E の分解能で丸めると −0.63 N になり、この説明と合う。実機の HEX-E でも同じことが起きるはずで、Sim2Real で確かめたい性質の例になる。
- 実時間の実行は、指令の届くステップの違いで軌跡が 2〜3 通りに分かれる。乱数の再現性は、指令を送らない静止状態で確かめるのが確実。

## 3. 後のフェーズの覚え書き

各フェーズの開始時に詳しく決めます。今は決めません。

- **力覚**
  - センサ本体の質量と厚みをモデルに入れるか（フェーズ 3 では入れていない）。
  - 手首と工具の切れ目が無い MJCF のために、site や body を入れる方法（手で書く、ツールで生成する、起動時に足す）。SO-101 では不要だった。
- **IMU**
  - 加速度（`cacc`）もフェーズ 2・3 と同じく、ステップの後に計算し直した値を使う。
- **測定値を制御に使う**
  - 今のコントローラは真値を読んでいます。
  - MuJoCo の位置サーボも、内部で真の角度を使っています。
- **gazebo**
  - 実装一覧の gazebo の対応項目は仮置きです。変換を作るときに確定させます。
  - 今の一覧では gazebo の力覚に `range` が無いが、hakoniwa の力覚の定義では `range` が必須。このままだと、同じ定義ファイルを gazebo で使えない。Gazebo の力覚にはレンジ（飽和）が無いので、変換を作るときにどう扱うかを決める。
