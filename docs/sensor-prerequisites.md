# センサ統合：全体像とフェーズ

Robot Runtime にセンサを統合する計画です。全体像を描いてフェーズに分け、簡単なものから 1 つずつ実証します。実証が通らなければ立ち止まり、通れば次のフェーズに進みます。

## 1. 全体像

```text
入力 → コントローラ → arbiter → actuator（plant.step） → sensor → publisher
```

- **sensor 段**は物理を 1 回進めるたびに、MuJoCo から真値を取り出し、センサの実装（アダプタ）に渡して測定値を得ます。
- **publisher** は、既存の出力と同じ仕組みで測定値を送ります。
- 実装は `hakoniwa` / `gazebo` / `airsim` から、センサごとに選べます。起動時に、実装一覧（`catalog/sensor-implementations.json`）と照合します。
- センサの定義ファイルは、どの実装でも共通の JSON です。
- センサを使うアプリケーションだけが、センサ機能を有効にし、実装のライブラリをリンクします。

取り付け方はセンサ種別ごとに違います。

| 種別 | 何に付けるか | MJCF に必要なもの |
|---|---|---|
| エンコーダ・関節トルク | 既存の関節 | 何も足さない（関節名で指定） |
| 力覚 | 2 つの剛体の切れ目（ロボットと工具の間） | 工具側が独立した body であること、センサ原点の site |
| IMU | 剛体の上の 1 点 | site |
| 地磁気・気圧・GPS | 剛体の上の 1 点 | site と、世界の地理的な基準点 |
| 測距・LiDAR・カメラ | 剛体の上の 1 点と向き | site と、ロボット自身に当たらない除外設定 |

センサの測定値をどの PDU のどの欄で送るかは [sensor-pdu.md](sensor-pdu.md) にまとめています（ROS の決まりに従う）。

### 2.1 フェーズ 1：エンコーダ

前提：

| 項目 | 内容 |
|---|---|
| 取り付け | 関節名で指定する。1 自由度の関節（hinge / slide）でなければ起動時にエラー |
| 真値 | 角度と角速度（関節の位置と速度）。トルクは扱わない |
| 時刻 | 物理を 1 回進めるたびに測る。周期は物理ステップに丸める |
| 出力 | JointState。真値の出力と区別できる名前にする |
| 制御 | 測って送るだけ。コントローラは今のまま |

実証の項目：

1. 誤差なしの設定で、測定値が真値と一致する。
2. STS3215 の設定（12 bit）で、測定値と真値の差が分解能（2π/4096 rad）の範囲に入る。
3. 同じシードで 2 回動かすと、測定値の列が一致する。
4. 定義ファイルに未サポートの項目があると、起動しない。
5. SO-101 のつかんで置く動作の間、測定値の JointState が PDU で受け取れる。

### 2.2 設定仕様（センサ種別に依存しない）

センサの定義は、種別によらず次の 3 つだけです。出力は publisher 側で別に定義します。

1. **何のセンサか**：`name`、`type`、`implementation`
2. **MJCF の何に、どの位置と姿勢で付けるか**：`mount`
3. **センサ仕様（ノイズなど）**：`definition`（共通の定義ファイルへの参照）

スキーマ：

- センサ：`schemas/components/sensor-instances.schema.json`
- 出力：`schemas/components/sensor-output.schema.json`

センサの例：

```json
{
  "$schema": "https://hakoniwa.dev/schemas/sensor-instances.schema.json",
  "schema_version": 1,
  "sensors": [
    {
      "name": "shoulder_pan_encoder",
      "type": "joint",
      "implementation": "hakoniwa",
      "mount": { "mjcf_joint": "shoulder_pan" },
      "definition": "../sensor-models/feetech_sts3215.json"
    },
    {
      "name": "wrist_ft",
      "type": "force_torque",
      "implementation": "hakoniwa",
      "mount": { "mjcf_body": "gripper", "position_m": [0, 0, 0.02],
                 "orientation_deg": { "roll": 0, "pitch": 0, "yaw": 0 } },
      "definition": "../sensor-models/onrobot_hex_e_qc.json"
    }
  ]
}
```

`mount` の書き方は 2 つです。センサ種別に合わない書き方は、スキーマでエラーになります。

| 書き方 | 使う種別 | 内容 |
|---|---|---|
| `mjcf_joint` | `joint` | 1 自由度の関節を測る。位置と姿勢はない |
| `mjcf_body` と `position_m`・`orientation_deg` | それ以外 | body に固定する。位置と姿勢は body 座標で表し、省略時は 0。センサ軸は FLU |

出力の例（6 関節をまとめて 1 つの JointState にする）：

```json
{
  "$schema": "https://hakoniwa.dev/schemas/sensor-output.schema.json",
  "schema_version": 1,
  "sensors": ["shoulder_pan_encoder", "shoulder_lift_encoder", "elbow_flex_encoder",
              "wrist_flex_encoder", "wrist_roll_encoder", "gripper_encoder"],
  "pdu_config": { "pdu_name": "joint_states_measured",
                  "message_type": "sensor_msgs/JointState", "update_rate_hz": 50.0 }
}
```

スキーマでは表せないため、起動時に検査する項目：

- 実装・種別・定義ファイルの項目・組み込み（実装一覧との照合）
- センサ名が Runtime 内で一意
- `mjcf_joint` が存在し、hinge か slide。`mjcf_body` が存在し、world ではない
- 出力の `sensors` の名前がすべて存在し、メッセージ型に合う種別（JointState なら `joint`）
- PDU 定義にチャンネルがあり、型が合う

その他：

- JointState の `name` には、センサが付いている MJCF の関節名を入れます。`position` と `velocity` に測定値を入れ、`effort` はフェーズ 1 では空にします。
- 乱数の系列は、全体のシード、ロボット名、センサ名から作ります。全体のシードは Runtime Config の `sensors.seed` に置き、省略時は 0 です。
- 出力のメッセージ型は、フェーズ 1 では `sensor_msgs/JointState` だけを許します。フェーズが進むたびに足します。

### 2.3 フェーズ 1 の実証結果（2026-11-11）

SO-101 の 6 関節にエンコーダを付け、Hakoniwa の上で標準デモと把持デモを流して確認しました。

| 項目 | 結果 |
|---|---|
| 1. 誤差なしで真値と一致 | 合格。530 時点、各関節が最大 1.35 rad 動く間、位置・速度の差が 0 |
| 2. STS3215（12 bit）で分解能の範囲 | 合格。位置の差の最大 7.664e-4 rad。分解能の半分（7.670e-4 rad）以内 |
| 3. 同じシードで同じ列 | 合格。ノイズ付き設定で 2 回動かし、3,018 サンプルで誤差の列が完全に一致。シードを変えると最大 2.1e-3 rad 違う |
| 4. 未サポートの項目で起動しない | 合格。8 種類の誤り（未サポート項目、綴り違い、未知の実装、関節センサを持たない実装、MJCF に無い関節、関節センサに body 用の取り付け、出力に無いセンサ名、PDU チャンネル無し）すべてで、原因を示して起動しない |
| 5. 把持デモの間、測定値が届く | 合格。42 秒間（手首は最大 4.8 rad 回転）、測定値の JointState が届き続け、誤差は分解能の半分以内 |

仕様（仮説）について分かったこと：

- センサの定義は「何のセンサか・どこに付けるか・定義ファイル」の 3 つで足りた。
- センサの実装は、時刻を 0 から物理ステップ単位で数える。Runtime の時刻はリセット後も 0 に戻らないことがあるため、sensor 段が自分で数えて、Runtime の時刻に換算する。
- 定義ファイルの先頭の `$schema` は、どの実装でも許す。
- Runtime の既存の読み込みは、知らない種類の部品を黙って読み飛ばしていた。センサ機能なしのビルドでセンサが書かれていたら、起動しないようにした。

- 実装名から実装を得る方法が、公開インタフェースに無かった（使う側が手書きのつなぎを書く必要があった）。hakoniwa-sensor-adapter に実装の名札（`SensorAdapterImplementation` と、実装名で決まる入口 `hako_sensor_adapter_implementation_<name>()`）を足した。Runtime は名札をそのまま登録し、アプリケーションのビルドは実装名の一覧から登録コードを生成する。
- 起動時に、実装一覧に書いた種別と、リンクした実装の名札が持つ種別の食い違いも検査する。
- 出力は ROS 2 と同じく `sensor_msgs/JointState`（ラジアン）。エンコーダのカウント値やフラグは JointState に欄がないので送らない。ドライバの層まで試したい用途が出たら、専用の型を足す。

残っていること：

- SO-101 のビルド設定と設定ファイルは hakoniwa-robot-arm の fork に置き、完成形にしてから本家へ PR を出す。

### 2.4 フェーズ 2：関節トルク（2026-11-11）

仮説：

- 設定は増やさない。関節センサの定義ファイルの `torque` 欄（測り方 `sensor` / `current`、レンジ、誤差、摩擦）で決まる。
- 真値は、関節を通って伝わるトルク（子の剛体の `cfrc_int` を関節の位置に移し、軸に投影したもの。親が子に及ぼす向き）。
- `mj_step` の直後は、力が 1 ステップ前の状態で計算されたままなので、トルクを測るセンサが 1 つでもあれば、ステップの後に `mj_forward` と `mj_rnePostConstraint` を 1 回だけ呼び、角度と同じ時刻の値にそろえる。
- 出力は同じ JointState の `effort`。1 つの出力のセンサは、全部トルクを測るか、全部測らないかにそろえる（混ざっていたら起動しない）。

実証（SO-101、Hakoniwa の上で標準デモと把持デモ）：

| 項目 | 結果 |
|---|---|
| 1. 静止状態で重力と一致 | 合格。401 時点で、記録した角度から質量と重心だけで独立に計算した重力トルクとの差は最大 1.2e-5 N·m（例：shoulder_lift −0.5388 N·m） |
| 2. 時刻がそろっている | 合格。同じモデルの Python 版で 2,000 ステップ比べ、Runtime と同じ方法は、新しく計算し直した値と完全に一致（差 0）。計算し直さないと、接触の瞬間などに最大 13.5 N·m ずれる。計算し直しても物理は変わらない（位置がビット単位で一致） |
| 3. 電流からの推定 | 合格。測定値は「最新の指令と、ステップ後の位置から出したアクチュエータ力 ＋ 摩擦」。真値の出力のアクチュエータ力は 1 ステップ前の位置で計算されたものなので、その差 kp·v·dt を補正すると、3,348 サンプルの中央値で 1.6e-12 N·m 以内。例外は 5 時点の 25 サンプル（最大 0.49 N·m）で、どれも速度が急に変わる所。サーボのダンピング項（kv × 1 ステップの速度変化）と考えられるが、2 ms 前後のサンプルが記録されていないため確認はしていない |
| 4. 再現性と検査 | 合格。トルクのノイズ付きで同じシードの 2 回は完全に一致（3,042 サンプル）、シードを変えると最大 0.26 N·m 違う。トルクを測るセンサと測らないセンサを 1 つの出力に混ぜると、理由を示して起動しない |
| 5. 把持デモ | 合格。キューブを持っている間、測定トルクから腕自身の重力トルクを引いた残りが、キューブ（30 g）の重さによるトルクとほぼ一致（shoulder_lift −0.060 対 −0.058〜−0.061 N·m、elbow −0.034〜−0.044 対 −0.037〜−0.041 N·m）。キューブの位置をグリッパー先端で近似したため、差は最大 1 割程度 |
| 6. 計算の増加 | SO-101 で 1 ステップ 12 µs → 23 µs（+11 µs）。物理ステップ 2 ms に対して 0.6 % |
| 物理への影響 | なし。Runtime 上でも、トルクを測る実行と測らない実行で、真値の軌跡が完全に一致（同じ到着タイミングの実行どうし、3,030 サンプル） |

分かったこと：

- 実時間で動かすと、軌道指令がどのステップで届くかで、軌跡が 2 通りに分かれる（今回の実行では最大 0.027 rad）。センサとは関係なく、比較は同じ到着タイミングの実行どうしで行う必要がある。
- 電流からの推定は「サーボが今の位置と最新の指令で出している力」で、実機のサーボと同じ時刻の値になっている。真値の出力にあるアクチュエータ力とは 1 ステップずれている。
- 外部センサプラグインのホスト側で、`mj_step` の直後に `mj_rnePostConstraint` だけを呼んで力を読むと、力やトルクが 1 ステップ古くなる。同じ方法を使っている箇所は別途直す。

### 2.5 フェーズ 3：力覚センサ（2026-11-11）

仮説：

- SO-101 の手首の回転関節で `wrist` につながる `gripper` body は、グリッパーの開閉用サーボと固定側の爪で、工具そのもの。手首と工具の切れ目はもうあり、MJCF の変更は要らない（前に「組み替えが要る」と書いたのは誤りだった）。
- 取り付けは body 用の書き方（`mjcf_body: gripper`、位置 [0, 0, 0]、姿勢 0）。姿勢は roll・pitch・yaw［度］で、R = Rz(yaw)·Ry(pitch)·Rx(roll)。
- 真値は、工具側（その body の部分木）がロボット側に及ぼす力とトルク。センサの軸で表し、トルクはセンサ原点まわり。時刻はフェーズ 2 と同じく、ステップの後に計算し直してそろえる。
- センサ本体の質量と厚みは入れない。
- 出力は `geometry_msgs/WrenchStamped`（PDU 登録集にある型）。1 つの出力に力覚センサ 1 つで、`frame_id` はセンサ名。出力の部品の種類名は、JointState 専用の `sensor_joint_state` から `sensor_output` に変え、型は `pdu_config.message_type` で決める。

実証（SO-101、Hakoniwa の上で標準デモと把持デモ）：

| 項目 | 結果 |
|---|---|
| 1. 静止状態で工具の重さと一致 | 合格。402 時点で、記録した角度から質量と重心だけで独立に計算した値との差は、力が最大 2.3e-5 N、トルクが最大 6.9e-7 N·m（力の大きさ 0.971 N ＝ 工具 0.099 kg の重さ） |
| 2. 時刻がそろっている | 合格。同じモデルの Python 版で、Runtime と同じ方法は新しく計算し直した値と完全に一致（差 0）。計算し直さないと、接触の瞬間などに最大 89.6 N ずれる |
| 3. 把持 | 合格。誤差なしの設定で、キューブを持っている間（123 時点）、世界座標に直した力から工具の重さを引いた残りの鉛直成分が平均 −0.2945 N（キューブの重さ −0.2943 N） |
| 4. OnRobot HEX-E の設定 | 静止中の力は分解能（xy 0.2 N、z 0.8 N）がノイズより粗いため一定値に丸まる。トルクのばらつきは、データシートのノイズ（σ0·√(B/B0)）と分解能から別に計算した値と合う（ty 0.0041 対 0.0038、tz 0.0015 対 0.0015、tx は平均が丸めの境目近くにずれていることを入れると 0.0050 対 0.0049〜0.0050）。平均のずれ自体（約 −0.003 N·m、クロストークと非線形と考えられる）は独立には確かめていない |
| 5. 再現性と検査 | 合格。静止状態（真値が完全に同じ）で、同じシードの 2 回は完全に一致（301 時点）、シードを変えると最大 1.6 N 違う。8 種類の誤り（力覚に関節用の取り付け、MJCF に無い body、world への取り付け、WrenchStamped の出力に関節センサ、WrenchStamped の出力に 2 つのセンサ、JointState の出力に力覚センサ、gazebo が対応しない項目、PDU チャンネル無し）すべてで、理由を示して起動しない |
| 6. 計算の増加 | フェーズ 2 と同じ計算し直し（+11 µs / ステップ）を使う。力覚センサが 1 つでもあれば 1 回だけ行う |

分かったこと：

- HEX-E の分解能では、30 g のキューブはほぼ見えない。キューブを持つと、鉛直方向の力はセンサの z 軸に乗り（約 −1.27 N）、z の分解能 0.8 N で −1.6 N に丸まる。そのため世界座標での増加は −0.58 N と、実際（−0.29 N）の約 2 倍に見える。誤差なしの測定値を HEX-E の分解能で丸めると −0.63 N になり、この説明と合う。実機の HEX-E でも同じことが起きるはずで、Sim2Real で確かめたい性質の例になる。
- 実時間の実行は、指令の届くステップの違いで軌跡が 2〜3 通りに分かれる。乱数の再現性は、指令を送らない静止状態で確かめるのが確実。

### 2.6 フェーズ 4：IMU（2026-11-11）

仮説：

- 箱庭の IMU モデルは箱庭ドローン PRO のセンサモデル（ジャイロ・加速度）。ドローン PRO 側は変えず、そのソースを参照してビルドし、実装「hakoniwa」の名札に載せる（コピーしないので二重管理にならない）。地磁気・気圧・GPS も同じく載る。
- IMU の定義ファイルは箱庭ドローン PRO の `drone_config` の形（`components.sensors.imu / gyro / acc`）。取り付けは Runtime の `mount` に書き、定義ファイルの `imu.mount` は 0。drone_config には `type` が無いので、起動時の検査はセンサの種類を Runtime の設定から取る（定義ファイルに `type` があれば一致を確かめる）。
- 取り付けは力覚と同じ body 用の書き方。真値は、センサ位置の角速度と比力（重力込みの加速度、理想的な加速度計の読み）で、センサの軸。比力は「その点の空間加速度 ＋ ω×v」で、MuJoCo の加速度計と同じ式。時刻はステップの後に計算し直してそろえる。
- 出力は `sensor_msgs/Imu`。IMU は姿勢を測らないので、ROS の決まりどおり `orientation_covariance[0] = -1`。ジャイロと加速度の両方が 1 回測るまでは送らない。

実証（SO-101、手首の 5 cm 先に取り付け）：

| 項目 | 結果 |
|---|---|
| 1. 静止状態で重力と一致 | 合格。415 時点で、記録した角度から独立に求めたセンサの軸での重力（＋9.81 上向き）との差は最大 9.2e-5 m/s²、角速度は最大 2.9e-6 rad/s |
| 2. 動いている間の一致 | 合格。同じモデルの Python 版で、同じ位置に MuJoCo 自身の加速度計とジャイロを置いて比べ、2,000 ステップ（加速度最大 152 m/s²、角速度最大 12 rad/s）で差は 2.8e-14 m/s²、1.8e-15 rad/s（計算機の丸めの範囲） |
| 3. ドローン PRO の IMU 設定 | 合格。ドローン PRO の評価用の設定（ノイズ・オフセット・ドリフト・分解能・フィルタ込み）で、静止状態の Runtime の出力と、同じ真値・同じシード・同じ名前でドローン PRO のモデルを直接動かした出力を比べた。起動直後 0.1 秒（腕がまだ重力で落ち着いていく間で、比べる側の真値を一定にしたため）を除き、すべて分解能 1 つ以内、62 % は完全一致 |
| 4. 再現性と検査 | 合格。静止状態で同じシードの 2 回は完全に一致（303 時点）、シードを変えると最大 0.60 違う。8 種類の誤り（IMU に関節用の取り付け、MJCF に無い body、drone_config 側に取り付けを書いた、IMU が使わない欄（baro）がある、WrenchStamped の出力に IMU、Imu の出力にエンコーダ、IMU を持たない実装、PDU チャンネル無し）すべてで、理由を示して起動しない |

分かったこと：

- 取り付け（body に位置と姿勢）と、センサの位置・向きの計算は、地磁気・気圧・GPS、測距・カメラでも同じものが使える。違うのは真値の取り出しだけ。地磁気には地球上の場所（磁場）が、測距・カメラにはレイと描画の部品（ロボット自身を除く設定と、描画するスレッド）が要る。
- gazebo の IMU は公開リポジトリにあるが、実装一覧には未登録。フェーズ 5 で足す。

### 2.7 フェーズ 4b：2D LiDAR（2026-11-12）

仮説：

- レイを飛ばす部品（ホストの部品）は hakoniwa-mujoco-robots の `IWorld` に置き、アクチュエータと同じく工場（`createRayCaster`）からインスタンスをもらう。センサ段は LiDAR ごとにもらい、LiDAR のアダプタに渡す。誤差モデル（LiDAR のアダプタ）は実装側に残る。部品は真値（何に、何 m 先で当たったか）だけを返し、どの向きに何本飛ばすかはアダプタが決める。
- センサ本体の筐体（LiDAR なら円柱）はモデルが持つ。取り付けの前に、筐体の body（関節なし、形状）を MJCF に入れ、センサはその body に、光学中心のずれで付ける。SO-101 では作業空間を作るツール（`sensor_housings`）で足す。
- レイは自分の筐体とその下には当たらない。アームは見える（実機と同じ。取り付け位置の検討に使える）。設定 `exclude_mjcf_body` で、さらに除く根の body を足せる（アームを `base` から隠す簡易テスト用）。
- 走査はステップの後の状態で行う（ステップの後に `mj_forward` を 1 回）。
- 出力は `sensor_msgs/LaserScan`。時刻は走査の最初のレイの時刻。

実証（SO-101、床に置いた筐体（半径 35 mm、高さ 40 mm）の上 5 mm、360 本、5 Hz）：

| 項目 | 結果 |
|---|---|
| 1. 部品の移植 | 合格。元の部品と同じモデル・同じレイで、8 body × 20 姿勢 × 360 本（57,600 本、当たり 32,998 本）の結果がビット単位で一致 |
| 2. 誤差なしの値 | 合格。Runtime が出した LaserScan を、記録した関節角でモデルを置き直し Python から直接 `mj_ray` で求めた値と比べ、360 本すべて一致（有限の 94 本の差は最大 2.2e-7 m、float32 の丸め）。前の壁、柱、キューブ、アームの台座と肩に当たる |
| 3. アームを隠す | 合格（直したあと）。`exclude_mjcf_body: base` で、アームの代わりにその奥の柱が見え、独立に求めた値と 360 本一致 |
| 4. 誤差（LDS-01 の定義） | 合格。30 スキャンで、0.5 m 以内のずれは標準偏差 14.7 mm（定義 15 mm）、0.5 m より遠くは距離の 4.93 %（定義 5 %） |
| 5. 再現性 | 合格。静止状態で同じシードの 2 回は 30 スキャンすべて一致 |

ミスマッチと解消：

- 3 で、最初は 360 本すべてが自分の筐体に当たった（距離 0.035 m、測れる範囲より近い）。部品が除く根を 1 つしか持たず、`base` を指定すると筐体の代わりになっていたため。筐体はワールドの直下にあり `base` の下ではない。除く根を配列にし、筐体はいつも除き、指定した根を足すように直した。既定の動き（1 の一致）は変わらない。

分かったこと：

- 取り付けとセンサの位置・向きの計算は IMU と同じものが使えた。違うのは、ワールドから部品をもらうことと、ステップの後に位置を計算し直すことだけ。測距（rangefinder）は同じ部品で足せる。
- 3D LiDAR と測距は同じ部品で足せた（2.8）。

### 2.8 フェーズ 4c：測距と 3D LiDAR（2026-11-12）

仮説：部品・取り付け・アダプタは 2D LiDAR と同じ。違うのは出力だけ。

- 測距（`rangefinder`）：`sensor_msgs/Range`。取り付けと除き方は LiDAR と同じ（`range_mount`）。
- 3D LiDAR：走査の結果を 2D と共通に持ち（格子と、返った点）、出力で選ぶ。`sensor_msgs/LaserScan` は 2D だけ、`sensor_msgs/PointCloud2` は 2D と 3D。点の欄は x, y, z, intensity（float32）、ring（uint16）、time（float32、走査の始まりから）。3D の定義（`scan.vertical` の `samples` が 2 以上）を LaserScan に出す設定は、起動時に止まる。

実証（SO-101、3D は 2D と同じ筐体で 16 段（±15°）× 360 本、測距はグリッパーの 5 cm 先で真下向き）：

| 項目 | 結果 |
|---|---|
| 1. 3D の誤差なしの値 | 合格。PointCloud2 の 3,400 点すべてが、独立に `mj_ray` で求めた距離と一致（差は最大 3.2e-8 m）。返るはずのレイの数も独立に数えて 3,400 本で一致。最初に 6 本違ったのは、比べる側のキューブを置いた直後の高さ（床に落ち着く前）にしていたためで、Runtime 側は正しかった |
| 2. 測距の誤差なしの値 | 合格。床までの距離 0.234111 m が、独立に求めた値と float32 の丸めの範囲で一致 |
| 3. 誤差 | 合格。3D は 102,000 点で標準偏差 29.7 mm（定義 30 mm）。測距は 228 回で 25.7 mm（定義 25 mm、分解能 10 mm） |
| 4. 再現性 | 合格。同じシードの 2 回で、3D は 30 スキャン、測距は 188 回すべて一致 |
| 5. 検査 | 合格。3D の LiDAR を LaserScan に出す設定は、理由を示して起動しない |

分かったこと：

- 出力部品が返すエラーは、ログに出るだけで Runtime は止まらない（ログは 256 バイトで切れる）。起動時に分かる誤りは、起動時の検査に入れる。

### 2.9 フェーズ 4d：地磁気・気圧・GPS（2026-11-12）

仮説：モデルは IMU と同じく箱庭ドローン PRO のもの（定義ファイルは drone_config の `components.sensors.mag`・`baro`・`gps`）で、取り付けも IMU と同じ。新しく要るのは、世界が地球のどこにあるかの設定（Runtime の設定 `sensors.world`：原点の緯度・経度・高さ、地磁気、海面の気象）だけ。MuJoCo の世界の軸は箱庭の決まりどおり NWU とする。

- 地磁気：設定の強さ・偏角・伏角から世界の磁場（NED から NWU）を作り、センサの軸に回す。
- 気圧：センサの海抜高度（原点の高さ ＋ センサの z）と海面の気象を渡す。
- GPS：アンテナの位置（NWU）と速度（その点の速度）を渡し、位置を WGS-84 に変換して一緒に渡す（ECEF を通す）。

実証（SO-101、グリッパーの 5 cm 先、原点は東京駅付近）：

| 項目 | 結果 |
|---|---|
| 1. 誤差なしの値 | 合格。記録した関節角から独立に求めた値と比べ、地磁気は差 5e-13 nT、気圧は差 0.0000 Pa（米国標準大気 1976 の同じ定義で計算）、GPS は独立の測地ライブラリ（pyproj）で変換した緯度・経度・高さと差 0.0000 mm |
| 2. 誤差（ドローン PRO の評価用の定義） | 合格。地磁気のばらつきは各軸約 300 nT（定義 300 nT）、ずれの平均はハードアイアン・ソフトアイアンの分。気圧のずれ -7.3 Pa は高度オフセット 0.5 m とドリフトの分、ばらつき 0.8 Pa。GPS のばらつきは北 0.49 m、上 0.81 m（定義 0.5 m、0.8 m）、共分散は精度 1.5 m・2.5 m の 2 乗 |
| 3. 再現性 | 合格。同じシードの 2 回で、3 つとも全部一致 |
| 4. 検査 | 合格。原点の無い気圧・GPS、地磁気の無い地磁気センサは、理由を示して起動しない |

分かったこと：

- 気圧の値を独立に確かめるときは、モデルと同じ大気の定義（米国標準大気 1976 の気体定数と、ジオポテンシャル高度）を使う。一般的な定数と幾何高度で計算すると 0.005 Pa（約 0.4 mm）ずれる。
- Runtime の設定のスキーマに、乱数の種（`sensors.seed`）が抜けていた。今回 `sensors.world` と一緒に足した。

### 2.10 カメラ：基礎設計（2026-11-12、実装前）

カメラは、描画の重さ・描くスレッド・描画の仕組みの違いがあり、ほかのセンサより前提が多い。実装の前に、今ある実装を基に分け方を決めた。

#### 今ある実装と、ランタイムの前提

| カメラの種類 | 今ある実装 | 前提／ランタイム |
|---|---|---|
| 深度 | `hakoniwa` 実装（レイで測る） | OpenGL なし。レイの部品（`IWorld::createRayCaster`）は作成済み。画像の出力（`Image` と `CameraInfo`）だけが要る |
| 深度 | `hakoniwa` 実装（描画）、hakoniwa-mujoco-robots のカメラ | 同じプロセスの OpenGL。描画の部品と、物理のスレッドからメインスレッドに頼んで待つ仕組みが要る |
| 深度 | 描画サーバー（Filament など） | 描画サービスへの頼み口（その歩の姿勢と動く物を渡して待つ）が要る。描画用の世界はサービスが持つ |
| RGB | `hakoniwa` 実装、hakoniwa-mujoco-robots のカメラ | 同じプロセスの OpenGL。上と同じ |
| RGB | 描画サーバー（Godot、Filament など） | 描画サービスへの頼み口が要る |
| RGBD・ステレオ | hakoniwa-mujoco-robots のカメラ | 種類にしない。同じ場所の RGB と深度、または間隔をあけた RGB 2 台として、センサを並べて表す |
| 塗り分け・物体番号 | 描画サーバー | 描画サービスへの頼み口と、塗り分けのセンサのインタフェースが要る |
| 3D の箱・動き・法線などの正解データ | 描画サーバー | 使う人が出てから決める |
| 魚眼・歪みレンズ | 描画サーバー | 種類ではなく、定義ファイルの特性。今ある簡易な実装はピンホールだけ |

- 描画で物理の結果は変わらない。撮る歩では、その歩の状態で撮り終わるまで次の歩に進まない（世界の時計は止まっている）。かかるのは実時間だけ。
- 同じプロセスの OpenGL：Runtime の物理は箱庭の asset スレッドで進み、メインスレッドはビューアが使う。macOS では GLFW の初期化とウィンドウ（見えないものも）の作成はメインスレッドだけなので、物理のスレッドからメインスレッドに頼んで待つ仕組みを Runtime の中に隠して持つ。

#### 決めたこと

1. **ユーザが選ぶのは、カメラの種類と実装。** レンズ・深度の意味・測り方などは定義ファイルの引数。RGBD とステレオは種類にしない。
2. **センサのインタフェースは種類ごと。** `IRgbCameraSensorAdapter`（既存）、`IDepthCameraSensorAdapter`（既存）、塗り分けのインタフェース（新規）。正解データ系は後。
3. **ホストの部品は 3 つで、実行のしかたの違いを隠す。**

   | インタフェース | 対応するカメラ | 前提 |
   |---|---|---|
   | `IRayCaster`（既存） | 深度（レイ） | OpenGL なし。スレッドの制約なし |
   | `IImageRenderer`（既存のまま） | RGB、深度（簡易な描画） | 同じプロセスの OpenGL、ピンホール。メインスレッドに頼んで待つ。拡張しない |
   | 描画サービスのインタフェース（新規） | RGB、深度、塗り分け（のちに正解データ系） | 描画サーバーへの頼み口。カメラ名・時刻・姿勢・出すもののビットマスク・動く物の一覧を渡して待つ（PDU 登録集の `RenderCameraFrame` の形）。カメラの特性（露出、光、天候、レンズ）はサービスのプロファイルが持つ |

4. **高度なカメラは「描画サービス」として扱う。** 実装はカタログで選び、定義ファイルはその実装のカメラの形（IMU が drone_config の形なのと同じ）。インタフェースは公開し、実装は隠せる。同じ頼み方に答えれば、別の描画サービスに差し替えられる。
5. 出力は ROS の型：RGB は `sensor_msgs/CompressedImage`、深度と塗り分けは `sensor_msgs/Image`、どれも `sensor_msgs/CameraInfo` と組。

#### フェーズ

| フェーズ | 内容 | 新しく要るもの |
|---|---|---|
| C1 | 深度をレイで測る（`hakoniwa` 実装、ピンホール） | 画像の出力（`Image`、`CameraInfo`） |
| C2 | 簡易な描画で RGB と深度（`IImageRenderer`） | ワールドからの描画の部品、メインスレッドに頼んで待つ仕組み、`CompressedImage` |
| C3 | 描画サービス（RGB、深度、塗り分け、レンズ） | 描画サービスのインタフェースと Runtime の頼み口、塗り分けのインタフェース |

範囲（2026-11-12 森）：MuJoCo の公式の配布物で使える描画（従来の OpenGL、`mjr`）で作れる、深度・RGB・ステレオに集中する。ユーザにソースからのビルドは求めない（公式の C/C++ の配布物では Filament の `mjrf` は使えない）。

#### C2 の基礎設計（2026-11-12、実装前）：描画は関数サーバー

RGB とステレオ（描画で撮るカメラ）は、描く人を 1 人に決め、描画を「頼むと絵が返る関数」として扱う。

- **関数サーバー**（hakoniwa-mujoco-robots）：OpenGL のコンテキストを持つのはメインスレッドの関数サーバーだけ。ビューアがあればその描画の輪の中で、無ければ見えないウィンドウで回す。頼みが来たら、画面の更新を待たずにすぐ起きて描く。
- **頼む側**（センサのアダプタ）：物理のスレッドから頼み、描き終わるまで待つ。待っている間、その歩の状態は止まっているので、描かれるのはその歩の世界。頼む前に `mjData` の mutex を手放す（握ったまま待つと、ビューアと行き詰まる）。
- **受け渡し**：同じプロセスの中は、キューと mutex・条件変数で素直に作る（RPC のライブラリは使わない。ポインタのまま渡せるので直列化もコピーも無い）。プロセスをまたぐ描画サービス（C3）は、箱庭の `hakoniwa-pdu-rpc` を使う。頼みの中身は同じ形にする。
- **バッファは頼む側が持つ**：頼みに書き込み先（ポインタと大きさ）を入れ、サーバーはそのメモリを信用して直接書く（GPU からの読み出し先がそのまま使う人のメモリ）。大きさが足りなければ書かずにエラー。OpenGL は下の行から読むので、書いた後にその場で行を入れ替える。

描画のインタフェース（公開、`IImageRenderer` を見直す）：

| 項目 | 決めたこと |
|---|---|
| 頼み | 1 枚ごとに、時刻、その歩のカメラの姿勢（世界 NWU、カメラの軸 FLU）、カメラの形（幅・高さ・内部パラメータ K・クリップ範囲）、出すもの（1 RGB、2 深度、4 塗り分け）、出すものごとの書き込み先 |
| 姿勢 | 頼みごとに渡す。描く部品は取り付け位置を覚えない（状態を持たない関数） |
| カメラの形 | `CameraInfo` と同じ K で渡す。レンズの歪みは簡易な描画では「できない」と能力で宣言し、カタログで起動時に止める |
| まとめて頼む | 同じ歩の複数台（ステレオなど）を 1 回で頼める |
| 呼ぶスレッド | どこからでもよい。メインスレッドへの受け渡しは実装が隠す |
| 能力 | 出せるもの・レンズを宣言する |

ロックの順番（仕様）：複数のロックを同時に持つときは、必ず次の順に取る。逆の順では取らない。

| 順 | ロック | 持ち主 |
|---|---|---|
| 1 | `mjData` の mutex（世界のロック） | Runtime の 1 歩（センサ段を含む）。ビューアは取らない |
| 2 | ビューア用の写しの mutex | 1 歩の終わりの写し（1 を握ったまま）、ビューアの描画（2 だけ） |
| 3 | 頼みのキューの mutex | キューへの出し入れ |
| 4 | 受け取り札ごとの mutex | 完了の知らせと待ち |

- ビューアは世界を直接読まない。Runtime が 1 歩の終わりに世界を写しにコピーし（画面の更新ほどの間隔、約 60 回/秒まで。リセットの後は必ず）、ビューアは写しを 2 だけ握って描く。ビューアが 1 を待つことが無いので、1 を握ったままカメラの完了を待つ 1 歩と、メインスレッドのビューアがお互いを待つことは無い。
- 3・4 は出し入れの間だけ短く握り、握ったまま描いたり他を待ったりしない。3・4 を握ったまま 1・2 を取らない。
- サーバーはカメラの頼みを処理する間、1 も 2 も取らない。`mjData` は 1 なしで読む（頼み手が 1 を握ったまま待っているので、その間は誰も世界を動かさない）。ビューアの描画の輪は、描くたびにカメラの頼みを処理する。
- 頼み手が 1 を握ったまま札を待ってよいのは、サーバーもビューアも 1 を必要としないから（唯一の例外）。

その他（2026-11-12 決定）：

- サーバーは頼みが来たら空のイベントで起こされ、画面の更新を待たずに処理する。
- カメラは画面のある環境で動くものとする（見えないウィンドウで描く）。macOS も Linux も同じ。画面の無い Linux、SSH だけでログインした Mac は対象外。
- RGB の出力は JPEG に圧縮した `sensor_msgs/CompressedImage` と `sensor_msgs/CameraInfo`。圧縮は出力の部品が `stb_image_write` で行う（外部センサプラグインと同じ部品）。画質は出力の設定 `jpeg_quality`（既定 95）。
- 組の基準は LiDAR と同じく筐体の body に取り付け、組の中の各カメラの位置は定義ファイルに書く。
- 深度カメラの描画方式（`method: render`）は、半透明の物も不透明として描く（MuJoCo は半透明の物に深度を書かないため。光線方式と同じく当たる）。透明度 0 の物は描かない。
- 描画方式は自分のロボットを除外しない。カメラの視野にロボットの部品が入らない位置（RGB と同じくカメラ筐体）に取り付ける。自分を除外したいときは光線方式を使う。
- 塗り分けなどの描画の道具（Python）は、センサのライブラリの範囲外。今回の実装は RGB の 1 台とステレオに絞る（深度の描画方式の組、塗り分け、描画サービスは後）。

カメラが複数あるとき：

- 同じ歩に撮るカメラは、センサ段が集めて 1 回のまとめた頼みにする。サーバーは 1 回だけ起きて順に描く。同じ頼みの中は同じ歩の状態（ステレオの左右がずれない）。
- 周期が違うカメラは、その歩に撮る番のものだけを頼みに入れる（撮る番はアダプタが決める）。
- 解像度が違うカメラ：MuJoCo の画面外描画の大きさの上限はモデルの `visual/global` の `offwidth`・`offheight` で、コンテキストを作るときに決まる。サーバーは起動時に全カメラの最大の解像度でバッファを作り、小さいカメラはその一部に描く（見た目の設定だけで、物理は変えない）。
- 頼みにはカメラの名前（センサ名）を入れる。エラーとログ、描画サービス（C3）でカメラの特性を引くのに使う。
- 1 つのプロセスに複数のロボットがいても、世界・物理のスレッド・サーバーは 1 つなので、同じまとめ方が効く。ランタイムのプロセスが分かれていれば、プロセスごとにサーバーを持つ。
- 頼みはリクエストキューに入れる。マルチスレッドに耐える作りにする：
  - 頼み手は何人でもよく、取り出すのはメインスレッドのサーバー 1 人。キューの出し入れは mutex、サーバーは条件変数で待つ（ビューアがあれば空のイベントで起こす）。
  - 頼み手は、まとめた頼みを入れて受け取り札をもらい、自分の札の完了だけを待つ（札ごとに完了の印を持つので、他の頼みに邪魔されない）。
  - 先に入れた頼みから描く。1 つのまとめた頼みは、途中に他の頼みを挟まずに続けて描く。
  - 頼みに「どの世界（モデルと状態）か」を入れ、サーバーは世界ごとに描画の準備（`mjrContext` など）を持つ。
  - 描いている間に世界が動かないことは、頼み手が待つことで守る。同じ世界を複数のスレッドが動かす場合の取り決めは、サーバーの外で決める。
  - 止まらないための決まり：サーバーが止まるときは残った頼みを全部失敗で返す。待つ時間に上限を持たせる。頼み手は、サーバーが要るロック（`mjData` の mutex など）を握ったまま待たない。
  - 偽のサーバーで、同時に頼んだ全員が自分の結果を受け取ること、まとめた頼みに割り込みがないこと、止まると失敗が返ることを確かめる（OpenGL なしで CI でも回せる）。
- 何台・どの解像度までリアルタイムを保てるかは、測ってここに書く。

ステレオカメラ（2026-11-12 見直し）：

- 新しい種類やインタフェースは作らない。RGB カメラのインタフェースを、最初から 1〜N 台のカメラの組（リグ）を扱える形にする。1 台なら普通のカメラ、2 台ならステレオ。
- 1 つのセンサ（アダプタ）が組を持つ。`step()` は組全体の姿勢を受け取り、N 枚の絵を返す（それぞれに `CameraInfo`）。アダプタは N 台分を 1 回の頼みにまとめて描画に頼むので、N 枚は必ず同じ歩の状態。誤差はカメラごとに別の乱数の列でのせる。
- 取り付け（Runtime の `mount`）は組の基準の位置と姿勢を 1 つ。カメラの数、組の中での各カメラの位置（基線長）、解像度、画角、雑音は定義ファイル（製品の性質。データシートに基線長がある）。
- 右の `CameraInfo` の P の基線長（ROS の決まり：`P[0][3] = -fx × 基線長`）は、アダプタが定義ファイルの位置から入れる。ステレオの決まりはセンサの仕様（hakoniwa-sensor-adapter）が持つ。左右の `frame_id` は別。
- Runtime の出力は、1 つのセンサから N 組の Image と CameraInfo を出せるようにする。PDU の出し方は、hakoniwa-mujoco-robots の TB3 用ステレオカメラ（`stereo_camera_sensor`）とそろえる。

RGBD カメラ：

- 種類は増やさない。RGB カメラと深度カメラのセンサを、同じ取り付け・同じ解像度と画角・同じ周期で置く。同じ姿勢と同じ K なので画素が 1 対 1 に対応する（ROS の位置合わせ済みの深度）。深度はレイ方式でも描画方式でもよい（どちらも同じ K で画素ごとのレイを作る）。
- 出力の設定に「RGBD の組」（RGB と深度のセンサ名）を書ける。起動時に、同じ取り付け・同じ K・同じ周期かを確かめ、合わなければ止まる。
- 周期がそろっているので、センサ段が同じ歩の頼みにまとめ、同じ状態で撮れる。
- 描画方式の深度と組むときは、同じ姿勢・同じカメラの頼みを「RGB と深度を出す」1 つにまとめられる（OpenGL は 1 回の描画で色と深度を出せる）。この速さの工夫は後から入れる。

今の `IImageRenderer` と、それを使うアダプタ（RGB、深度の描画方式）は、この形に合わせて直す。

#### C1 の実証（2026-11-12）：深度カメラをレイで

仮説：深度カメラは LiDAR と同じ設計。取り付け（測距用の body）、ワールドのレイの部品、`hakoniwa` 実装のアダプタ（`method: ray`、誤差モデルとシードはアダプタ側）はそのまま。新しいのは出力だけ：`sensor_msgs/Image`（32FC1）と `sensor_msgs/CameraInfo` を同じ時刻で 2 つのチャンネルに出す（出力の設定に `camera_info_pdu_name`）。

| 項目 | 結果 |
|---|---|
| 1. 誤差なしの値 | 合格。グリッパーから真下（64×48）で 3,072 画素すべて、筐体から斜め（64×48）で有限の 1,491 画素すべてが、CameraInfo の K から画素ごとのレイを作って独立に `mj_ray` で求めた光軸方向の距離と一致（差は最大 5.5e-8 m）。床・キューブ・アーム・爪が写る |
| 2. 出力 | 合格。Image と CameraInfo の時刻が同じ。画素の中心は整数の座標（ROS の決まり） |
| 3. 誤差 | 合格。ばらつき 9.97 mm（定義 10 mm）、全画素が分解能 1 mm の格子に乗る |
| 4. 再現性 | 合格。同じシードの 2 回で 21 枚すべて一致 |
| 5. 検査 | 合格。描画で測る定義（`method: render`）は、描画の部品が無いので理由を示して起動しない |
| 6. 速さ | 合格（筐体に付けたとき）。10 Hz で、64×48 は実時間 6 秒でシミュレーション 6.00 秒、320×240（約 77,000 本）は 5.98 秒 |

ミスマッチと解消：

- 最初、グリッパーのメッシュの中に付けると、シミュレーションが実時間の約 0.35 倍に落ちた。レイが自分のメッシュ（見た目用と当たり判定用が重なる）を平均 2.2 枚くぐって打ち直すため。ありえない取り付けはユーザの問題として止めず、起動時に警告を出すことにした（森）。レイを使うセンサごとに、原点から 26 方向へ試しに撃ち、自分の面を平均 1 枚（筐体の壁）より多くくぐれば `[WARN]` を出す。筐体に付ければ警告は出ず、実時間を保つ。
