# 箱庭 vs ROS 2 / Gazebo 比較レポート（2026-11-13）

同じ条件で並べて測ると、箱庭は通信の速さと CPU で ROS 2・Gazebo を上回り、実機の LiDAR で起きる失敗もシミュレーションで再現できました。比べる中で、箱庭自身の弱点も見つけて直しています。

## 結論

通信・掴んで置く作業・LiDAR の 3 つで、箱庭は数字で言える強みを持ちました。Gazebo も掴んで置く作業はすべて通しており、「負かした」ではなく「同じ土俵で得意と不得意を示せた」結果です。

| 比べたもの | 箱庭 | 相手 | 言えること |
| --- | --- | --- | --- |
| 通信の遅延（1 MB・100 Hz、点群） | 0.70 ms | ROS 2 1.6 ms、Gazebo の通信 2.5 ms | 大きいデータほど差が開く |
| 負荷が高いとき（4 MB・1000 Hz） | 壊れない。最新の値だけ届く | ROS 2 ゼロコピーは壊れたデータ 94 個、Gazebo は遅れが 0.2 秒まで積み上がる | 壊れ方の違いがはっきりした |
| 掴んで置く（センサーと MoveIt） | 3 / 3 成功、CPU 0.90 コア | Gazebo 3 / 3 成功、CPU 1.22 コア | 結果は同じ、CPU は箱庭が約 3/4 |
| 回転する LiDAR | 動く腕の点群が歪み、MoveIt が腕を障害物と見間違える（21 回中 4 回失敗） | Gazebo の LiDAR は一瞬で撮るので起きない | 実機で起きる失敗が、実機の前に見える |

測ったのは Mac の Docker（6 コア、GPU なし）と SO-101 の 1 つの組み合わせで、センサーにノイズは入れていません。

## 通信

同じプログラムで通信の部分だけを入れ替え、送ってから受け取るまでの遅延を測りました。1 KB から 4 MB、10・100・1000 Hz を各 3 回。箱庭は 100 µs ごとに受信を確かめる設定です。測り方と道具は `tools/transport-bench`（ブランチ feat/transport-bench）にあります。

**点群（型変換あり、100 Hz、遅延の中央値）**

| データ | Gazebo の通信 | ROS 2（標準） | 箱庭 |
| --- | --- | --- | --- |
| 1 KB | 0.37 ms | 0.34 ms | 0.16 ms |
| 320 KB | 1.0 ms | 0.65 ms | 0.28 ms |
| 1 MB | 2.5 ms | 1.6 ms | 0.70 ms |
| 4 MB | 4.1 ms | 5.5 ms | 2.9 ms |

**固定サイズ（変換なし、ROS 2 はゼロコピー、遅延の中央値）**

| データ・周期 | Gazebo の通信 | ROS 2 ゼロコピー | 箱庭 |
| --- | --- | --- | --- |
| 1 MB・100 Hz | 2.4 ms | 0.33 ms | 0.17 ms |
| 4 MB・100 Hz | 4.0 ms | 0.42 ms | 0.27 ms |
| 4 MB・1000 Hz | 約 210 ms（遅れが積み上がる） | 0.16 ms（ただし壊れたデータ 94 個） | 0.30 ms（壊れ 0、取りこぼし 6〜8 個） |

- 箱庭は、ほぼすべての条件で遅延が一番小さく、送信側の CPU は ROS 2 の 1/2〜1/10 でした。負けたのは 4 MB・1000 Hz の中央値だけです。
- 負荷が高いときの崩れ方が、それぞれ違います。箱庭は最新の値だけが届き、壊れず遅れません。ROS 2 は取りこぼし、ゼロコピーでは中身が壊れることがあります。Gazebo の通信は全部届きますが、遅れが積み上がります。
- どれも同じマシンの中の通信です。シミュレーション全体の速さを比べたものではありません。

## 掴んで置く（センサーと MoveIt）

同じスクリプトで、30 mm・30 g の立方体を掴んで運びました。MoveIt が天井の 3D LiDAR から障害物の地図を作り、手首の力センサで掴めたかを確かめます。13 段のどこかで失敗すると止まります。

Gazebo には箱庭と同じ作業場（床、壁、柱、立方体、LiDAR、力センサ）を作り、摩擦の組み合わせと、物に触れるのが爪のパッドだけであることもそろえました。条件と手順の詳細は [evaluation-gazebo.md](evaluation-gazebo.md) の 3.4 と 5.1 にあります。

| | 箱庭（LiDAR 回転） | 箱庭（LiDAR 一瞬） | Gazebo |
| --- | --- | --- | --- |
| 13 段すべて OK | 3 / 3 | 3 / 3 | 3 / 3 |
| CPU（全体、コア） | 0.90 | 0.82 | 1.22 |
| 物理のプロセス（コア） | 0.15 | 0.14 | 0.65 |
| 閉じた爪の角度 | 0.279 rad | 0.279 rad | 0.285 rad |
| 持ち上げたときの力の変化（重さ 0.294 N） | 0.294〜0.295 N | 0.294〜0.295 N | 0.294 N |

- 掴む物理は、どちらも同じように動きました。1 回にかかる時間も同じくらい（53〜61 秒）です。
- CPU は箱庭が Gazebo の約 3/4 でした。ただし、後述の空回りを直す前は、箱庭のほうが約 4 割多かったです。

## LiDAR の時刻のずれ

箱庭の回転する LiDAR は、動いている腕を実機のように歪んだ点群で撮り、それが MoveIt の失敗につながりました。箱庭で 21 回流して 4 回、MoveIt が腕を運ぶ途中で「障害物とぶつかる」として止まりました。その障害物は、自分の腕です。

1. LiDAR は 0.5 秒かけて 1 周を測り、点群には測り始めの時刻が付きます。
2. MoveIt は、その時刻の腕の位置で、点群から自分の体を消します。
3. 測っている間に腕が動いた分の点は消えず、障害物の地図に残ります。
4. 残った点が、これから腕が通る道にかかると、MoveIt が動きを止めます。

MoveIt が自分の体を消した後、腕のまわりに残った点の数（1 スキャンあたり、各 3 回）：

| | 腕が動いているとき（平均 / 最大） | 止まっているとき（平均 / 最大） |
| --- | --- | --- |
| 箱庭（LiDAR 回転） | 21.1 / 296 | 1.1 / 3 |
| 箱庭（LiDAR 一瞬） | 1.7 / 42 | 0.9 / 3 |
| Gazebo（LiDAR 一瞬） | 0 / 0 | 0 / 0 |

- 残るのは腕が動いているときだけで、一瞬で撮る方式にすると平均で約 1/12 に減りました。箱庭は、設定 1 行でこの 2 つを切り替えられます。
- 実機の回転する LiDAR でも起きること（動きによる点群の歪み）です。Gazebo の標準の LiDAR は一瞬で撮るので、この失敗は出ません。ただし、回転を再現する LiDAR は CARLA や Isaac Sim にもあるので、「箱庭だけ」とは言いません。
- 箱庭の点群には、実機の LiDAR のドライバと同じく、点ごとに測った時刻（`time`）が既に付いています。根本の手当ては、それを使って点ごとの時刻の腕の位置で消す（または歪みを直す）ことです。MoveIt の標準の消し方は、点ごとの時刻を見ません。点群の時刻を 1 つずらしても直りません。
- 一瞬で撮っても、動いているときに最大 42 点残りました。点群が届く時刻と、腕の位置の更新の差と見ていますが、まだ確かめていません。

## 比べて直したこと

相手と同じ条件で並べたことで、箱庭の弱点も見つかりました。

| 見つかったこと | 原因 | どうしたか |
| --- | --- | --- |
| 掴んで置く作業で、箱庭の CPU が Gazebo より約 4 割多い | 時刻を進める役（コンダクター）が、待つ間も眠らずに 1 コアを使い切っていた | 既にある「待つ間は眠る」設定を有効にした。物理のプロセスは 112 % → 18 %、配信の速さは変わらず。箱庭のコアで根本に直すのはこれから |
| 4 MB の点群で、箱庭の型変換が遅い（変換なしの約 10 倍） | 毎回の大きなメモリ確保とゼロ埋め、コピーの回数（見立て） | 変換部品の課題として登録。内訳を測ってから直す |
| 掴んで置くスクリプトが、起動直後にたまに失敗 | 座標変換（TF）が届く前に問い合わせていた | 届くまで待つようにした |

どれも、自分たちだけで測っていたら「動いた」で終わっていたものです。

## 次にやること

- **Isaac Sim との比較**：通信、掴んで置く作業、LiDAR の時刻を、今回と同じ型で比べる。見せ方は「GPU なしでここまでできる」。
- **点ごとの時刻を使う**：箱庭の点群に既にある点ごとの時刻で歪みを直す（デスキュー）処理を作る。歪みが起きる → 失敗する → 補正して直る、までをシミュレーションで示せる。
- **実機に近いと言うために**（実機なしでできる順）
    1. SO-101 の公開されている実機の記録と、関節の動きを比べる
    2. 実在する LiDAR と力センサの仕様書の値で、ノイズと分解能を入れる
    3. ノイズを強くしながら、掴んで置く作業がどこまで通るかを測る
- **箱庭のコアの空回り**を根本から直す。今は設定で避けている。
